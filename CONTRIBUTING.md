# Участие в разработке

Принимаются сообщения и pull requests на русском и английском. Для существенного изменения сначала опишите задачу в Issue: это помогает согласовать поведение и не дублировать работу.

## Подготовка

1. Создайте fork и рабочую ветку от `main`.
2. Используйте отдельное виртуальное окружение Python 3.11 или новее.
3. Для ядра установите `python -m pip install -e .`; для GUI — `python -m pip install -e ".[desktop]"`.
4. На Windows запускайте `python gemini_gui.py`. Готовые EXE собираются на Windows x64 с Python 3.13 и `requirements-build.lock`.

Команды предполагают Python активированного окружения. В PowerShell без активации используйте `.venv\Scripts\python` вместо `python`.

## Границы модулей

- Обнаружение, протоколы и команды находятся в `miner_scanner`; ядро не импортирует Qt.
- Интерфейс и пользовательские настройки находятся в `desktop_ui` и `gemini_gui.py`.
- Новый вариант прошивки начинайте с профиля и обезличенного примера ответа. [Пошаговая инструкция](docs/development/adding_device.md).
- Не добавляйте перебор управляющих команд наугад. Поддержка чтения не подтверждает поддержку записи.
- Отсутствующие показатели остаются неизвестными: не подменяйте их нулями, не смешивайте единицы хешрейта.
- Изменения форматов настроек должны сохранять чтение старых файлов и не перезаписывать пользовательские данные при ошибке.

## Проверки перед PR

```shell
python scripts/check_scanner.py
```

Скрипт проверяет синтаксис и запускает `unittest`. Тесты не должны обращаться к рабочим ASIC или внешним API. Локальный TCP-эмулятор допустим. Для тестов файлов используйте временный каталог; не читайте личные диапазоны, пароли и настройки.

Для изменений GUI на Windows:

```powershell
python gemini_gui.py --smoke-test artifacts/ui-preview
```

Посмотрите снимки в светлой и тёмной темах; проверьте небольшое окно, клавиатурную навигацию, ошибки ввода и отмену. Для релиза используйте `python scripts/build_windows.py`: он дополнительно проверяет уже собранный EXE и экспорт отчётов.

## Что приложить к PR

- Проблему и итоговое поведение; для ошибки — способ воспроизведения.
- Выполненные проверки и их результат.
- Для GUI — снимки до/после с демонстрационными данными.
- Для устройства — точную модель и версию прошивки, обезличенный ответ API, источник сведений и статус аппаратной проверки.
- Для изменения поведения — соответствующее обновление документации.

Пишите небольшие изменения с одной понятной задачей. Используйте понятные имена и разделяйте сетевую логику, разбор данных и интерфейс. Новые тесты должны проверять поведение, ошибки или границы совместимости.

Не включайте в PR EXE, виртуальные окружения, базы SQLite, личные настройки, сетевые дампы с настоящими адресами, пароли, токены и кошельки. `dist` публикуется через Releases. Номер версии и тег меняются при подготовке релиза, а не в каждом PR.

## Выпуск релиза

Владелец сверяет версии в `gemini_gui.py`, `pyproject.toml` и `version.json`, запускает сборку и публикует тег на **коммите с этой версией**. Не создавайте новый тег на старом коммите. Опубликованные теги не перемещайте без отдельного согласования с владельцем.

Подробности: [Windows-релиз](docs/development/windows_release.md).
