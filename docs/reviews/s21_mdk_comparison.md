# Antminer S21: сравнение ASIC Monitor и Tether MDK

Дата: 20 сентября 2026 года. Статус: исследование кода и проверки с подменёнными транспортами; аппаратных испытаний не было.

Сравнивались:

- ASIC Monitor: коммит `685241de126d70323144d3f00844ef021be1e96a`.
- Tether MDK: коммит `bae810a1370f327c1270a9e7c7b32bd2db745b2a` ветки `main`.
- Наши справочники, тесты и существующий сетевой дамп S21+.

## Вывод

MDK полезен как источник реализации HTTP API Antminer и форматов ответов. Нашему сканеру действительно не хватает такого пути чтения S21. При этом у нас уже есть поиск по подсетям, выбор профиля, ограничения запросов и осторожная обработка команд. Заменять весь сканер на MDK по результатам этого сравнения не требуется.

Самое существенное расхождение управления — **разные ключи записи режима сна**. Код MDK не доказывает, какой вариант принимает конкретная прошивка нашего S21. Нужны точная сборка и обезличенная запись обмена с её веб-интерфейсом.

## 1. Поиск устройств и выбор профиля

| Вопрос | ASIC Monitor | MDK Antminer |
|---|---|---|
| Откуда берутся устройства | Диапазоны IPv4/CIDR, исключения, ограниченный пул потоков | Адреса заранее зарегистрированных устройств |
| Выбор модели | По ответам устройства и сигнатурам семейства | Модель задаётся при запуске worker: `s19xp`, `s19xp_h`, `s21`, `s21pro` |
| Сведения о прошивке | Чтение известных полей; предусмотрено сопоставление профиля с точными версиями | Чтение версии есть; отдельного выбора формата команд по версии прошивки в исследованном Antminer worker нет |
| S21+ | Семейный профиль может распознать имя; отдельной аппаратной квалификации нет | В перечне моделей worker S21+ отдельно не заявлен |

В MDK обнаружение worker ядром и обнаружение ASIC в подсети — разные процессы. В исследованном пути `startAntminerWorker → provisioning → plugin.connect` устройства берутся из хранилища/`seedDevices`; модель задаёт оператор. Поэтому этот worker сам по себе не заменяет нашу функцию сканирования диапазона. Источники: [запуск MDK worker][mdk-boot], [подключение устройства][mdk-connect], наш [ScannerService](../../miner_scanner/service.py).

Наш [реестр профилей](../../miner_scanner/profiles/__init__.py) умеет ограничивать команды точной моделью и сборкой, но для S21 такой подтверждённый профиль сейчас не заполнен. В `bitmain.stock` список `verified_commands` пуст. В GUI выполнение непроверенных команд требует отдельного разрешения для выбранных устройств. Это **механизм будущей совместимости**, а не доказательство поддержки всех прошивок.

### Подтверждённые пробелы нашего пути HTTP

На искусственном устройстве с недоступным 4028, доступными `get_system_info.cgi`/`get_miner_conf.cgi` и ответами современного HTTP-формата воспроизведено:

- устройство идентифицировано как `Antminer S21`, но строка таблицы содержит `Antminer Unknown`;
- HTTP-методы `summary.cgi` и `stats.cgi` вообще не запрашиваются;
- хешрейт отсутствует (`None`), однако строка получает `Error / NO HASH`, `stale=False`;
- даже при прямой передаче HTTP-данных текущему парсеру хешрейт и массивы температур/вентиляторов не разбираются;
- один ответ с `miner_type` и `fw_version` не идентифицирует Antminer: ключ `miner_type` отсутствует в списках идентификации.

Это конкретный дефект обработки **недоступной телеметрии**: отсутствие измерения нельзя выдавать за измеренный нулевой хешрейт. Результат относится к указанному сценарию, а не ко всем S21. Если устройство отдаёт поддерживаемые ответы CGMiner, наш текущий путь работает.

Исправления потребуются в `service.py`, `profiles`, `drivers.py`, `normalization.py` и парсере. Одного добавления URL в JSON-профиль недостаточно.

## 3. Управление

### Сон и возобновление майнинга

Оба проекта обращаются к `get_miner_conf.cgi`, затем к `set_miner_conf.cgi`. Однако тело записи отличается:

| Этап | ASIC Monitor, текущая ветка S21 | MDK |
|---|---|---|
| Чтение конфигурации | `bitmain-work-mode`, `bitmain-freq-level` | Те же исходные поля |
| Запись режима | `bitmain-work-mode: 1/0` | `miner-mode: 1/0` |
| Поле частоты в записи | `bitmain-freq-level` | `freq-level` |
| Проверка результата | Повторное чтение поля режима | В методе смены режима отсутствует |

Наш [`mode_payload`](../../miner_scanner/commands.py) сохраняет конфигурацию, проверяет обязательные поля и отказывает при маскированных значениях. Но наличие поля в **ответе чтения** само по себе не устанавливает название поля в **запросе записи**. В [имитаторе MDK][mdk-mock] это специально разные поля. Наш существующий тест воспроизводит наш вариант и не может разрешить спор о настоящей прошивке.

Дополнительно на неизменённых методах MDK с подменой `fetch` воспроизведены:

1. `setPowerMode('sleep')` возвращает `success: true` до завершения POST.
2. Ответ POST с `ok: false` не меняет этот результат.
3. `reboot()` возвращает `success: true` даже при отклонении запроса транспортом.

Это результаты проверки методов драйвера, не испытание всей инфраструктуры MDK. [Обработчик смены режима worker][mdk-mode-handler] непосредственно передаёт результат метода. Поэтому копировать такую семантику успеха в наш агент нельзя.

У нас смена режима подтверждается **полем конфигурации**, что ещё не гарантирует фактическую остановку/возобновление хеширования. Для расписаний нужна следующая стадия: подтверждать состояние по последующим измерениям, отдельно показывая «настройка принята» и «устройство достигло нужного состояния».

### Остальные команды

| Функция | Результат сравнения |
|---|---|
| LED | Основной запрос совпадает: `blink.cgi`, JSON `blink: true/false`. MDK дополнительно читает `get_blink_status.cgi` и ставит таймер выключения. У нас нет такого чтения в профиле; результат принятого запроса остаётся неподтверждённым. |
| Reboot | Endpoint совпадает. У нас принятый запрос или timeout не считаются доказанной перезагрузкой. Нужны возврат того же устройства и уменьшение uptime. |
| Low / HEM | В нашем штатном S21-профиле отсутствуют. В Antminer-контракте MDK объявлены только `sleep/normal`; проверенный метод отвергает `low`. Общие константы SDK не означают поддержку функции S21. |
| Настройка пулов | В MDK есть `setupPools`. В текущем публичном диспетчере команд нашего сканера такой операции нет. |
| Полный журнал ASIC | README MDK упоминает `downloadLogs`, но в исследованных Antminer-контракте и обработчиках реализации этой команды не найдено. Наш диагностический ZIP также не является полным kernel log. |

Источники: наши [команды](../../miner_scanner/commands.py), [диагностика](../../miner_scanner/diagnostics.py); [контракт MDK][mdk-contract], [README Antminer][mdk-antminer-readme], [проверки команд MDK][mdk-unit-tests].

## 4. Скорость и нагрузка

У нас уже есть ограничения параллелизма между устройствами, срок операции, размер ответа и кэш метаданных. На существующем синтетическом S21 первый опрос сделал 7 запросов, повторный — 3. Это количество вызовов подменённого транспорта, **не измерение скорости на площадке**.

MDK собирает полный снимок несколькими запросами с ограничением параллельности; отдельные обработчики используют [кэш чтения](https://github.com/tetherto/mdk/blob/bae810a1370f327c1270a9e7c7b32bd2db745b2a/backend/core/mdk/lib/things/miner.js#L126). Нельзя сравнивать время полного снимка MDK и нашего короткого опроса без одинакового набора данных.

Практичные улучшения для нас:

- выбирать рабочий транспорт чтения при идентификации и кэшировать этот выбор;
- не повторять заведомо недоступный CGMiner в той же операции: сейчас после отказа в discovery сбор профиля снова вызывает его;
- отдельно обновлять быстрые метрики и редкие сведения о прошивке/пулах;
- ограничивать число одновременных запросов к одному ASIC; величину подбирать на оборудовании;
- измерять длительность цикла, таймауты, запросы на устройство и долю неполных снимков.

## 6. Порядок доработки

### Сначала — корректное чтение

1. Добавить HTTP-ветку Antminer с распознаванием `miner_type`, явным разбором `summary/stats/pools` и единиц измерения. Сохранить работающий путь CGMiner.
2. Выбирать парсер по наблюдаемой структуре ответа; хранить источник метрик и качество снимка.
3. Согласовать модель в строке таблицы с идентификацией. Отсутствующие данные показывать как неизвестные; нулевой хешрейт считать измерением только при наличии соответствующего поля.
4. Поддержать оба исследованных формата `/warning` отдельными правилами.
5. Расширить разрешённые чтения и список безопасных полей диагностического экспорта. Сейчас он не собирает перечисленные новые CGI и не сохраняет некоторые текстовые поля версии.

### Затем — точные команды

6. На одной конкретной модели/сборке записать запрос штатного веб-интерфейса на сон и пробуждение, включая JSON и ответ; удалить секреты.
7. В профиле независимо задать поля чтения, записи и проверки, обязательные поля конфигурации и условия применимости.
8. Проверить неизменность пулов и остальных настроек, отказ авторизации, HTTP 200 без смены режима, timeout без повторной записи, фактические переходы сна/запуска.
9. Только после испытаний внести конкретные команды в `verified_commands`. S21, S21+, S21 Pro и альтернативные прошивки квалифицировать отдельно.

Критерий готовности: таблица корректно показывает устройство при доступном CGMiner и при доступном только HTTP; потеря метрик не выглядит как авария хешрейта; команды выбираются по подтверждённому профилю; отчёт о результате различает принятие настройки и фактическое состояние ASIC.

В рамках этого исследования рабочие драйверы, интерфейс и сервер не изменялись.
