# WhatsMiner RPC 3: контракт пулов и границы проверки

Актуализировано 09.11.2026. Относится к локальной программе и RPC 3 на TCP 4433.
Команда настройки пулов документирована; отсутствие паролей в ответе чтения
не означает, что изменить пулы невозможно. При записи неизвестные пароли
необходимо явно задать. Совместимость выбранного формата проверяется отдельно;
управляющие запросы в описанной аппаратной проверке не отправлялись.

## Что устанавливает RPC 3

`set.miner.pools` принимает зашифрованный `param`: JSON-массив до трёх объектов
с полями `pool`, `worker`, `passwd`. Внешний запрос содержит `cmd`, `ts`, `token`,
`account`, `param`. SHA256 вычисляется от последовательной конкатенации команды,
пароля API, salt и timestamp. Это **не HMAC**. Первые восемь символов Base64
дайджеста образуют token, полный дайджест — ключ AES-256. Кадр RPC предваряется
четырёхбайтовой длиной JSON в little-endian.

Пароль API и пароль пула — разные значения. Документированный положительный ответ
записи содержит целочисленный `code=0` и соответствующий `desc`; он означает
приём операции, а не независимое подтверждение сохранения настроек.

## Шифрование известно, примеры противоречат друг другу

Проверенный официальный Python demo использует AES-256-ECB с PKCS7.
[Версионный код производителя](https://github.com/whatsminer/whatsminer-mdk-worker/blob/a47fa82020454f9bfa9963ccaaa319b7948e8aa2/lib/protocols/wm-api-v3.js#L126)
также явно задаёт ECB и PKCS7 и сериализует логический параметр один раз.
Это достаточное основание называть PKCS7 подтверждённым форматом эталонного клиента.

При этом опубликованный производителем пример шифротекста соответствует
75 байтам JSON и пяти нулевым байтам дополнения. Офлайн-проверка воспроизвела
этот шифротекст с нулевым дополнением, но не с PKCS7. Такой же пример уже присутствует
в архиве документации 2025-03-04; это не доказательство различия прошивок 2026 года.
Приём обоих вариантов конкретным устройством не проверен. Автоматически пробовать
несколько записей на основании этого расхождения нельзя.

Независимая повторная проверка текущего `https://apidoc.whatsminer.com/`
09.11.2026 дала тот же результат: 80 расшифрованных байт, из которых первые
75 совпадают с опубликованным JSON, последние 5 — нулевые, не PKCS7.
SHA256 текущего `assets/main.bundle.js?v=1786701667319`:
`291d4ccd2342fd30ba42b39f51963ad8e7c08894c58b999c0287accb36c43b0a`.
Разбор строк документации и AES-проверка выполнены только офлайн; публичные
примерные значения не становятся учётными данными программы.

В локальном demo есть отдельная ошибка композиции: `set_miner_pools` передаёт
`json.dumps(paramload)` в `_encrypt_param`, который снова вызывает `json.dumps`.
Получается JSON-строка вместо описанного массива. Копировать эту цепочку нельзя.
Замечание о длине символов само по себе не доказывает ошибку padding: стандартный
`json.dumps` здесь формирует ASCII благодаря `ensure_ascii=True`.

## Пароль необходимо передать явно

Документированное чтение `get.miner.status` с `param="pools"` возвращает runtime-поля
пулов, включая адрес и account, но не `passwd`. `get.miner.setting` описывает режимы,
мощность и настройки запуска; полного списка сохранённых пулов с паролями там нет.
Документация не устанавливает, что пропущенный пароль, слот или поле при записи
означает сохранение существующего значения. Подставлять пустую строку или `x` нельзя.

Редактор может изменить worker или URL, если пользователь явно задаёт пароль
для каждого отправляемого слота. RPC3-ветка передаёт все три слота целиком:
пароли нужны также для пулов, URL и worker которых сохраняются. Это отдельный
ввод в рамках операции, а не подмена неизвестного значения. Пароль учётной
записи API не используется вместо пароля пула.

Явно введённое пустое значение передаётся как пустое; выбранное действие
«не менять» не означает пустой пароль. Введённые пробелы, пунктуация, Unicode
или строка из звёздочек — буквальные значения пользователя и не обрезаются.
Если обязательный пароль не задан, отказ относится к конкретному плану,
а не к невозможности настройки данной аппаратной модели.

## Реализация и предел подтверждения

[`whatsminer_pool_backend.py`](../../miner_scanner/whatsminer_pool_backend.py)
реализует выбранный контракт эталонных клиентов: один JSON-массив
`pool/worker/passwd`, однократная сериализация, ASCII JSON с escaping Unicode,
AES-256-ECB и PKCS7 по байтам, Base64 и один `set.miner.pools`. Вариант с нулевым
дополнением и двойная сериализация demo не используются. Ключ и token
формируются из свежего salt и времени; пароли и сырой запрос не сохраняются
в обычном журнале.

Перед записью вновь проверяются профиль, модель, фактические версии API/прошивки,
API Write, порядок ID 1–3, URL/worker и автоматический суффикс. Несовпадение
с предпросмотром останавливает план. Нужны учётная запись API с правом setter
и криптобиблиотека; включённый API Write сам по себе не доказывает это право.
Операция не включает API Write, не меняет права и не перезапускает устройство.

Непустой `btrom-worker-suffix` блокирует **любую** запись пулов этой веткой,
включая изменение только URL или пароля: все три runtime account снова
отправляются как worker, а совпадение runtime account с сохранённым базовым
именем при активном суффиксе не доказано. Иначе прошивка может дописать
суффикс повторно. В описанном чтении M50 этот параметр был пустым.

После отправки читается реальный `get.miner.status:pools`, а не локальный
кэш отправленных значений. Совпадение URL/worker позволяет показать их в работе,
но не подтверждает пароль или постоянное сохранение конфигурации.
Поэтому даже положительный ack и совпавший runtime readback остаются
`unconfirmed`, с отдельным признаком `accepted_by_api`. Потеря ответа не вызывает
повтора setter, другого padding или автоматического отката.

[Офлайн-интеграция](../../tests/test_whatsminer_pool_integration.py) проверяет
путь реального planner/backend на подменённом RPC с независимым дешифрованием:
точные три пароля, один массив, token, PKCS7, runtime-only итог и запрет replay.
Независимый запуск `python -B -m unittest tests.test_whatsminer_pool_integration`
успешно пройден 09.11.2026. Это программная проверка на подменённом RPC,
не аппаратная отметка и не проверка реального сокета. Применение PKCS7 и запись пулов на реальном
M50/M60/M61 либо другой модели в этой задаче пока не проверены.

## Чтение M50_VH75, 09.11.2026

На отдельно согласованном устройстве установлены модель `M50_VH75`, прошивка
`20260908.12.Rel2`, API `3.0.5`. Последний обезличенный RPC-прогон содержит четыре запроса `get.*`:
два `get.device.info`, `get.miner.status`/`pools` и `get.miner.setting`.
Флаг API Write был включён, но его изменение, записи настроек и перезапуски не выполнялись.

Получены три runtime-записи с ID 1, 2, 3 и документированными полями
`id`, `url`, `status`, `account`, `stratum-active`, `reject-percent`, `last-share-time`.
Пароля нет во всех трёх. Чтение настроек завершилось с `code=0`, корректным `desc`
и пустым `btrom-worker-suffix`. Соответствие ID сохранённым слотам и их порядок после
перезапуска этим наблюдением не доказываются; общий алгоритм индексов не изменён.

[Fixture](../../tests/fixtures/whatsminer_m50_rpc3_pools_read.json) содержит только
синтетические значения и наблюдённые технические метаданные/структуру.
[Тесты](../../tests/test_whatsminer_pool_observed.py) проверяют чтение и отображение
трёх записей. Отсутствие паролей требует отдельного явного ввода для новой операции;
сам read-only прогон не является проверкой setter. Аппаратная запись не проверена.

Исследования TCP 8889 и старых прошивок остаются отдельными. Их ключи, разрешения
и поля не используются для RPC 3. MDK и лабораторные программы не являются
зависимостями Python-мониторинга; для описанного чтения не требуется AES-библиотека.
Запись использует `cryptography`; без неё план не отправляется. Прямой импорт
официального demo и его зависимостей в приложение не нужен.
