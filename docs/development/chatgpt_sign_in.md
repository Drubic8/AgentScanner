# Вход через ChatGPT в локальном ASIC Monitor

Подключение в текущих исходниках использует официальный Sign in with ChatGPT для
открытого локального приложения. Оно не входит в уже опубликованный Windows
релиз `v2.6.0`. Общий диагностический skill, очистка входа, предпросмотр и
проверка заключения остаются общими с [механизмом ИИ-анализа](ai_analysis.md).

Пользователь выбирает **ChatGPT** в настройках и проходит вход в системном
браузере. Это подключение аккаунта с разрешением использовать подходящий план
ChatGPT. API-ключ OpenAI, клиентский секрет или пароль ChatGPT программа не
запрашивает. Наличие аккаунта или успешная проверка личности сами по себе не
означают, что OpenAI разрешил использование плана. Условия открытого локального
и платного размещённого приложения различаются.
[Область применимости механизма](https://developers.openai.com/siwc/token-sharing-open-source).

## Компоненты

- `miner_scanner.ai.chatgpt_auth` — браузерная авторизация, локальный callback,
  проверка личности и разрешения плана, обновление и отзыв сессии.
- `desktop_ui.chatgpt_store.ChatGPTStore` — отдельные защищённые записи
  регистраций и активный аккаунт.
- `miner_scanner.ai.openai.OpenAIProvider` — список моделей выбранного аккаунта,
  пробный запрос и анализ через Responses API.
- `miner_scanner.ai.https_transport` — ограниченные HTTPS-запросы только к
  явно разрешённым серверам, проверка TLS и имени, отмена и ограничения размера.
- Панели настроек и карточки — ручной запуск входа/запроса и состояние фоновых
  операций. Открытие окна само по себе не начинает вход или анализ.

## Авторизация и доверие

Перед первым входом сохраняется случайный идентификатор хоста. Для каждой
попытки создаются новые `state`, `nonce` и PKCE S256. Локальный HTTP-слушатель
открывается только на `127.0.0.1` и свободном порту, с фиксированным путём
`/auth/callback`. Callback проверяет Host, путь, однократность и `state` до
использования кода или ошибки. Адрес callback с тем же портом применяется при
обмене кода.

Браузер открывается до первого HTTPS-запроса программы. OIDC discovery
выполняется после проверки callback, перед обменом кода и проверкой ID token.
Зависимости `PyJWT[crypto]` проверяются до начала входа; при их отсутствии
возвращается `auth_dependency_missing`, а не предложение сначала выбрать модель.
Статусы подготовки, ожидания браузера и проверки входа передаются в GUI отдельно
от адреса авторизации. Повторное открытие браузера использует только текущую
попытку; её адрес не записывается в настройки или журнал.

Первый вход регистрирует клиент; дальнейший вход использует сохранённый
выданный `client_id` выбранной регистрации. Смена аккаунта не смешивает токены
других регистраций. Новая попытка становится активной только после проверки
личности. Подпись ID token проверяется по ключам OpenAI с ограниченными
алгоритмами; проверяются issuer, audience, срок действия и nonce. При повторном
входе также сверяется subject выбранного аккаунта.
[Контракт авторизации](https://developers.openai.com/siwc/token-sharing-open-source/sign-in).

Доступ к моделям требует разрешения `chatgpt.tokens.use.direct` из ответа
token endpoint. Разрешение в callback не подменяет выданные scopes. Access и
refresh token не помещаются в URL; сохранённый ID token может использоваться
только как подсказка следующего входа в OpenAI. Авторизационный URL, код callback
и токены не выводятся в журналы приложения.

## Хранение, обновление и выход

Записи находятся в `chatgpt_credentials.dat` рядом с остальными настройками
программы и шифруются Windows DPAPI для текущего пользователя. Каждая запись
содержит свою проверенную личность, выданный client ID, токены, scopes и срок
действия. `email` служит подписью в интерфейсе; идентичность регистрации не
определяется только совпадением email. Файл записывается атомарно. Открытого
резервного формата нет.

`.chatgpt-host.json` содержит непрозрачный идентификатор этой установки, а не
токен. `chatgpt_credentials.dat.lock` служит для межпроцессной синхронизации.
Сеансовые файлы не переносят вход на другой ПК или другого пользователя Windows.
Токены не включаются в обычный JSON настроек, диагностический пакет или Git.

Обновление access token сериализуется блокировками между потоками и процессами.
Новый access token, его срок, scopes и заменяющий refresh token сохраняются
вместе. Терминальный отказ обновления отключает локальную авторизацию; временная
ошибка сети не заменяет сеанс другим способом оплаты. При выходе выполняется
попытка отзыва refresh token и очищаются локальные токены выбранной регистрации.
Если отзыв не подтверждён, интерфейс сообщает об этом и предлагает проверить
подключения в ChatGPT. Регистрация и идентификатор хоста сохраняются для
повторного входа.
[Жизненный цикл аккаунтов и сеансов](https://developers.openai.com/siwc/token-sharing-open-source/profiles-and-sessions).

## Модели и Responses API

Каталог получается через `GET https://api.openai.com/v1/models` с OAuth access
token. Для этого пути ожидается массив `models`; видимые варианты определяются
`visibility: "list"`, а идентификатор модели — `slug`. Это отличается от обычного
каталога API с массивом `data`. Провайдер сохраняет порядок сервера и проверяет,
что выбранная модель по-прежнему доступна текущему аккаунту.

Запрос анализа направляется только в
`POST https://api.openai.com/v1/responses`: точная инструкция из предпросмотра,
массив `input` с очищенными данными, `store: false`, `stream: true` и
`text.format: {type: "json_schema", name: "asic_diagnostic_report", strict: true,
schema: OUTPUT_SCHEMA}`. Проверка подключения использует собственную небольшую
схему, а не диагностическую. Инструменты
управления ASIC, произвольная сеть, hosted MCP и продолжение чужой переписки не
подключены. Ключ API и платёжный маршрут не используются как автоматическая
замена отказавшему плану ChatGPT.
[Модели и выполнение запросов](https://developers.openai.com/siwc/token-sharing-open-source/models-and-inference).

Необязательный старый режим `text.format: {type: "json_object"}` не отправляется.
Диагностический ответ ограничивается строгой JSON Schema и дополнительно
проверяется локально. Некорректный ответ не показывается как заключение;
автоматического исправляющего запроса нет.

Финальный текст извлекается из сообщений `phase: "final_answer"`; промежуточные
`commentary` не склеиваются с ним. Ответ старого формата без `phase` допустим при
отсутствии промежуточных сообщений. Отказы, инструменты и отражение токенов
проверяются также в пропускаемых сообщениях. Само завершение потока не заменяет
проверку схемы и ссылок на реально переданные строки и показания.
[Структурированные ответы](https://developers.openai.com/api/docs/guides/structured-outputs?api-mode=responses),
[фазы сообщений](https://developers.openai.com/api/reference/resources/responses/methods/retrieve).

Событие `response.metadata` принимается как служебное до или после завершения,
включая маркер `[DONE]`, и не используется как текст ответа или признак успеха.
Перед пропуском сохраняются проверки JSON и отражения токенов; активные поля
вывода внутри этого события запрещены. Ошибка, отказ, команда или новый вывод
после завершённого ответа по-прежнему отменяют результат.

Для HTTP 200 от фиксированного inference-маршрута заголовок `Content-Type`
не служит единственной причиной отказа: тело в любом случае проходит полный
ограниченный разбор SSE. Обычный HTML/JSON, оборванный поток или отсутствие
`response.completed` не принимаются. Проверка MIME каталога моделей и
авторизации сохраняется.

Общий валидатор допускает ссылку на существующий элемент массива снимка,
например `snapshot.telemetry.fan_rpm[0]`, и единственный полный блок
` ```json ` без постороннего текста. Отсутствующие поля и индексы, пропущенные
строки лога, несколько блоков и дубликаты ключей по-прежнему отклоняются.
Безопасные `validation_stage`, `validation_reason` и `validation_field`
показывают конкретное место отказа, не сохраняя ответ модели в журнал.

Ошибка может содержать отдельную неизменяемую карту технических сведений:
HTTP-статус, проверенные `error.code`, `error.param`, request ID и тип конверта
ответа. В интерфейсе отображаются только разрешённые идентификаторы, а не
произвольный текст `error.message` или `detail`: сервер может вернуть в них
фрагменты входа. Токены и их JSON-экранированные отражения проверяются до
извлечения сведений. Временный отказ запроса не удаляет сохранённый вход.

Текущий OAuth-путь не принимает часть обычных параметров Responses, включая
`max_output_tokens` и `temperature`. Они не отправляются. Размер результата
ограничивается локально; ограничение не является гарантией стоимости
запроса у провайдера. Поток SSE читается в ограниченный буфер: до 2 МиБ на поток
и 256 КиБ на одно событие, затем разбирается без показа частичного заключения.
Успех возможен только после `response.completed` с завершённым ответом.
Оборванный поток, `response.failed`, `response.incomplete`, отказ модели и
результаты инструментов не считаются успешной диагностикой.
[Ограничения текущего механизма](https://developers.openai.com/siwc/token-sharing-open-source/preview-limitations).

Безопасные коды различают отсутствие разрешения, недоступный аккаунту механизм,
лимит плана, недоступность проверки лимита, неверный маршрут и ограничения
операции. Текст произвольной серверной ошибки не показывается. Запрос анализа
не повторяется автоматически; ошибка после начала SSE также отменяет результат.
Токены в обычном или JSON-экранированном виде в ответе отклоняются.
[Ошибки и восстановление](https://developers.openai.com/siwc/token-sharing-open-source/errors-and-recovery).

Системное DNS-разрешение остаётся исключением для немедленной отмены. TCP-адреса
делят один бюджет, а ожидание TLS/заголовков/тела прерывается наблюдателем
конкретного запроса. Закрытие окна ожидает завершения фоновой операции.

## Проверка и запуск из исходников

Для Windows рекомендуется Python 3.13. Откройте PowerShell в папке, где хотите
хранить проект, и создайте собственное окружение:

```powershell
git clone https://github.com/Drubic8/AgentScanner.git
cd AgentScanner
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -e ".[desktop]"
.\.venv\Scripts\python.exe gemini_gui.py
```

Команда установки включает Qt и `PyJWT[crypto]` для проверки безопасного входа.
При обновлении существующей копии повторите установку зависимостей и полностью
перезапустите программу. Опубликованный EXE 2.6.0 и Android APK 2.5.0 не получают
эти функции при одном лишь обновлении исходников.

Проверки используют искусственный OIDC-сервер в подменённом HTTPS-транспорте,
временный loopback callback, тестовые подписи и SSE-ответы. Они проверяют
контракты и отрицательные сценарии.

2 ноября 2026 года отдельно проверен полный цикл входа и анализа через ChatGPT
на синтетических данных: принято заключение с семью проверенными ссылками на
переданные свидетельства. Ответ повторно проверен локально через карточку,
копирование и сохранение TXT без нового запроса. Это проверка работоспособности
анализа из исходников на конкретном подключении,
а не точности диагностики всех ASIC или доступности для любого аккаунта.

Пошаговая настройка — в [руководстве пользователя](../user_guide_chatgpt.md).
