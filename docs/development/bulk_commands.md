# Массовые команды: отправка и подтверждение

## Предварительная проверка и экран результатов

Windows сначала запускает `PreflightWorker` и `miner_scanner.preflight.preflight_batch`:
до 32 параллельных опросов с принудительной идентификацией. Для каждого уникального
IP возвращается `PreflightResult`: исходная копия выбранной строки, актуальный
снимок при его наличии, статус готовности и объяснение. На этом этапе нет записи
команд или намерения управления в журнал ядра. Опрос может обновлять кэш телеметрии
и выполнять обычную авторизацию чтения.

`command_support` используется и предварительной проверкой, и окончательной
отправкой. Проверяются правила интерфейса, явные запреты, проверенные команды
профиля и допустимый экспериментальный доступ. Права записи до управляющего
запроса не считаются доказанными. Экспериментальное разрешение помечается отдельным
объяснением и не обходится через явный запрет интерфейса.

`desktop_ui.command_batch_dialog.CommandBatchDialog` хранит исходные цели и
обновляет модель таблицы по IP. Только явное нажатие **Отправить для N** запускает
`ActionWorker` с готовой частью пакета. Перед каждой записью по-прежнему выполняется
повторная идентификация; исходный `Identity.fingerprint` передаётся в
`dispatch_command(expected_fingerprint=...)`, поэтому обновление кэша между
выбором и отправкой не отменяет проверку версии/паспорта выбранной строки.

Результаты доставляются отдельно от обновления основной таблицы:
`dispatched_signal` — завершён этап подготовки/отправки (включая отказы),
`command_result_signal` — конечный `CommandResult` конкретного IP. Счётчик этапа
отправки не утверждает, что каждому адресу уже отправлен сетевой запрос записи.
Неожиданное исключение одного задания не прерывает остальные адреса и не делает
неопределённый исход успешным. Исключения публикуются без удалённого текста,
который мог содержать учётные данные.

Повторный пакет формируется только через `is_retry_safe`: отмена до записи,
пропуск или явный отказ API без положительного подтверждения. Общий `failed`
не доказывает отсутствие записи и не даёт права повторять запрос. Повтор всегда
снова проходит предварительную проверку и явное подтверждение; старый набор
выбранных устройств и успешные IP в него не добавляются. Автоматического повтора
нет. Остановка использует `Event`; уже отправленные операции остаются с реальным
подтверждённым либо неопределённым исходом.

Новые проверки: `tests.test_command_preflight`, `tests.test_command_batch_dialog`,
`tests.test_bulk_commands_gui`. Они работают с подменёнными транспортами, без ASIC.

## Что изменено

Раньше `ActionWorker` занимал один из восьми потоков на весь цикл:
повторное определение устройства → запись → проверка → обновление всей телеметрии.
Следующий ASIC ждал освобождения такого потока, даже когда запись предыдущему
давно завершилась.

Теперь `miner_scanner.batch.execute_batch` разделяет работу:

1. До 32 потоков готовят и отправляют команды. Настройка GUI позволяет уменьшить
   это число до 1; общий семафор ограничивает отправку между несколькими пакетами.
2. Отдельные 16 потоков подтверждают состояние чтением API. Первый запрос идёт
   сразу; повторные чтения — через 1 и ещё 2 секунды, в пределах сетевого бюджета.
3. GUI обновляет телеметрию отдельными 8 потоками, не задерживая отправку или
   журналирование результата команды.

В одном пакете одновременно находятся не более 512 операций, включая ожидающие
проверки. Это позволяет отправить пакет из 500 устройств, пока его проверки
ещё ожидают ответов. Для больших пакетов действует ограничение очереди.
Таймауты сетевых операций действуют отдельно на подготовку/запись (до 30 секунд)
и проверку (до 30 секунд); ожидание свободного потока не расходует этот бюджет.
Фактические отдельные запросы и предварительный опрос имеют более короткие лимиты.

## Сохранённые гарантии

- Идентичность устройства, выбранная строка, совместимость API и учётные данные
  проверяются перед записью. Смена устройства или прошивки не обходится ради скорости.
- Намерение выполнить запись сохраняется в журнале до обращения к API управления.
- Команда записи не повторяется автоматически после таймаута. Повторный
  `command_id` использует сохранённый результат.
- Для одного IP подготовка, запись и подтверждение защищены общей блокировкой
  команды. Второй запрос, например `wakeup` вслед за `sleep`, ждёт завершения первого.
- Блокировка отдельного опроса (`RLock`) захватывается и освобождается в одном
  потоке. Отправка и подтверждение последовательно используют одну сессию;
  одновременно к ней никто не обращается.
- Закрытие генератора или отмена освобождает сессии и блокировки. Отправленная
  команда с незавершённой проверкой остаётся неподтверждённой.
- `execute_command` сохраняет синхронный интерфейс для существующих вызывающих
  модулей. Новая очередь не подключает автоматически расписания агента или Android.

`on_dispatch` сообщает о завершении этапа отправки и наличии положительного
ответа API. Итоговые результаты генератора отдельно сообщают `succeeded`,
`unconfirmed`, `unsupported`, `skipped`, `failed` или `cancelled`.
`succeeded` означает подтверждённое состояние API, а не окончание разгона хешрейта.

## Проверка без оборудования

```powershell
python -m unittest tests.test_command_batch tests.test_mixed_mining_commands tests.test_desktop_release tests.test_identify
```

В `test_500_dispatches_finish_while_verification_is_blocked` все чтения результата
намеренно задерживаются. Проверяется, что запись всем 500 уникальным синтетическим
устройствам заканчивается до снятия задержки, а итоговый успех не появляется
раньше подтверждения. Также проверяются отмена, закрытие потребителя, дубли IP,
повторные команды, отрицательные ответы и освобождение ресурсов.

Тест смешанных моделей выполняет сон и пробуждение через реальные обработчики
Stock L9, T21, WhatsMiner RPC и Avalon на подменённых транспортных ответах. Проверка
GUI задерживает обновление таблицы и убеждается, что оно не останавливает очередь
или публикацию результатов. Сетевых обращений к настоящим ASIC в этих тестах нет.

Это проверка очереди и протокольной логики, не измерение времени управления
500 реальными ASIC. До применения расписаний на площадке нужно измерить время
подготовки, последней отправки и подтверждения на её устройствах и сети.
