# Elphapex: доказательства контракта настройки пулов

Проверено **9 ноября 2026 года**. Есть два отдельных источника:
статическое чтение официальной программы и согласованное чтение одного
DG1+ с разбором его текущей веб-формы. Программа производителя и JavaScript
не исполнялись. Записи настроек на ASIC и аппаратного подтверждения
изменения пулов не было. Контракты этих двух источников различаются.

## Чтение и запись

| Этап | Установленный путь в программе | Ограничение доказательства |
| --- | --- | --- |
| Чтение | `GET /cgi-bin/luci/get_miner_conf.cgi` | Для выбранного DG1+ V1.0.4 получена полная обезличенная схема; это не подтверждает запись и совместимость всех DG1/DG1+ |
| Слоты | `pools[0]`, `[1]`, `[2]`, поля `url`, `user`, `pass` | Клиент предполагает все три позиции; это не доказательство отсутствующих/скрытых паролей у каждой прошивки |
| Запись | `POST /cgi-bin/luci/set_miner_conf2.cgi` | Именно `conf2`, а не выведенное по аналогии имя `set_miner_conf.cgi` |
| Тело | JSON UTF-8; `Content-Type: application/json`; три pool objects | В теле также присутствуют значения других полей DTO, описанные ниже |
| Авторизация клиента | Новый `HttpClient` без настроенных credentials/Authorization в этих методах | Не утверждается доступность без авторизации на всех прошивках; 401/403 остаются отказом доступа |
| Принятие | HTTP 200, JSON с `stats == "success"` | В методе нет дополнительного ограничения `code`; код успеха конкретного ASIC не наблюдался |
| Применение | В pool-ветке `asyncConfig` явного reboot нет; режим работы изменяется отдельным запросом только при выбранном действии | Нет доказанного времени применения и независимой проверки сохранения после записи |

Точные точки статического результата:

- `decompiled-interface/LTCTool.InterfaceComm.decompiled.cs`: `getMinerPools`,
  строки 324–354, читает три URL/user/pass. `httpGetAsync`/`asyncCheckAndGet`
  возвращают текст без замены дефисов подчёркиваниями.
- `decompiled-main/LTCTool.LTCTool.decompiled.cs`: `httpPostAsync`, строки 816–845;
  `updateminerConfRootobject`, 2357–2475; `asyncConfig`, 2478–2557.
- `decompiled-dto/LTCTool.minerConfRootobject.decompiled.cs` и
  `decompiled-dto/LTCTool.Pool.decompiled.cs` — точные объявления полей.

Номера относятся к этим локальным результатам ILSpy, а не к исходным файлам
производителя. Для перепроверки используются метод, SHA256 сборки и содержимое,
поскольку другая версия декомпилятора может иначе пронумеровать строки.

## Имена и типы полей DTO

У класса `minerConfRootobject` нет `JsonProperty` и других объявленных aliases.
Это перепроверено с доступной декомпилятору метадатой поставляемой
`Newtonsoft.Json.dll`. В `Program.Main` нет настройки `JsonConvert.DefaultSettings`.

| Имя свойства / JSON-ключ по умолчанию | Тип CLR | Что делает pool-ветка записи |
| --- | --- | --- |
| `fc_fan_ctrl` | `bool` | Не присваивает; новое DTO оставляет `false` |
| `fc_fan_pwm` | `string` | Не присваивает; остаётся `null` |
| `fc_freq` | `string` | Не присваивает; остаётся `null` |
| `fc_voltage` | `string` | Не присваивает; остаётся `null` |
| `fc_work_mode` | `string` | Не присваивает; остаётся `null` |
| `fc_freq_level` | `string` | Не присваивает; остаётся `null` |
| `pools` | массив `Pool` | Создаёт три позиции и присваивает значения |
| `Pool.url`, `Pool.user`, `Pool.pass` | строки | Из нового ввода либо уже прочитанного состояния выбранного устройства |

Затем используется обычный `JsonConvert.SerializeObject` созданного DTO.
Иными словами, найденный код **не** показывает full-config RMW с сохранением
вентиляторов, режима, частот и напряжения. Нельзя копировать его `false`/`null`
в продукт как будто это прежние значения устройства.

Для незаданных слотов `updateminerConfRootobject` берёт URL/user/pass из
состояния выбранного ASIC; если строка неизвестна/пуста, исходный инструмент
подставляет `""`. Такое преобразование не годится для гарантии сохранения
скрытого пароля. Автоматическое изменение suffix у исходного инструмента
также не переносится: программа должна показывать точное итоговое имя.

## Модели, версии и ещё не установленное соответствие

В `LTCTool_Init` есть записи DG1 и DG1+; pool-метод не проверяет точную сборку
прошивки и не доказывает отдельную совместимость DG1/DG1+ каждой версии.
Словарь поддерживаемых моделей или название утилиты не заменяет проверку
интерфейса устройства.

В существующих исходниках и тестах мониторинга чтение режима Elphapex использует
`fc-work-mode` с дефисами. Прежние тесты режимов содержат только нужный им
фрагмент и пулы; новая полная схема выбранного DG1+ приведена ниже.
Из схемы чтения нельзя вывести преобразования
`fc-work-mode → fc_work_mode` или аналогичные замены остальных ключей.

Для отдельного старого пути `luci/...conf2` остаются обязательные условия:

1. Полная обезличенная форма ответа DG1/DG1+ выбранного API: точные wire keys,
   типы, три позиции, известный/скрытый/отсутствующий `pass`.
2. Доказанное соответствие этих полей телу `set_miner_conf2.cgi`. Нужен либо
   подтверждённый полный read-to-write map, либо доказательство, что этот
   endpoint сохраняет опущенные nonpool-поля. Наличие старого инструмента,
   отправляющего `false`/`null`, само по себе этого не доказывает.
3. Проверка неизменности режима, вентиляторов, частот/напряжения, неизвестных
   дополнительных полей и двух нетронутых слотов. Незнакомая схема блокирует
   запись; неизвестный пароль не становится пустым.
4. Однократная запись и свежее чтение конфигурации после неё; ack без readback
   не становится подтверждённым сохранением. Таймаут не вызывает повторную запись.

До выполнения этих условий официальный инструмент даёт точный
**кандидат старого контракта**, но не основание автоматически включить
`luci/...conf2` для существующего Elphapex профиля. Текущая форма ниже
использует другой путь и не наследует его DTO. Операции записи на реальном
ASIC требуют отдельно согласованных адресов и действий.

## Текущая веб-форма DG1+ / DG1+_SW_V1.0.4

Позднее 09.11.2026 пользователь предоставил отдельный DG1+ для чтения.
Подтверждены модель DG1+, Stock `DG1+_SW_V1.0.4`, профиль `elphapex.luci`.
Конфигурация содержит ровно восемь полей: три `pools` с присутствующими
строковыми `url/user/pass`, `fc-fan-ctrl` boolean, `fc-work-mode` integer,
строковые `fc-voltage`, `fc-freq-level`, `fc-fan-pwm`, `fc-freq`, `algo`.
Дополнительных полей нет. Значения настроек, паролей, MAC/SN не сохранялись.

Основные `/` и `/index.html` требуют HTTP Basic. После отдельного
разрешения пользователя выполнены только GET с авторизацией для этого
устройства; получены основная HTML и локальные модули. Значения доступа
в доказательства не включены. Статически установлен маршрут `/miner`
и его компонент `/assets/Miner-f770af99.js`, использующий Axios 1.5.0.

| Шаг | Точное поведение текущей формы |
| --- | --- |
| Чтение | `GET /cgi-bin/get_miner_conf.cgi`; весь `response.data` становится состоянием формы |
| Поля пулов | Три объекта `pools`, прямые привязки строк `url`, `user`, `pass` |
| Запись | `POST /cgi-bin/set_miner_conf.cgi`, JSON всего текущего объекта, `Content-Type: application/json` |
| Nonpool | Не создаёт DTO и не подставляет defaults; передаёт все остальные свойства объекта с их текущими типами |
| После HTTP 2xx | Запускает новый GET и сразу показывает Success; тело ответа и завершение readback не проверяет |
| Применение | В компоненте нет отдельного apply, reboot или таймера |

В компоненте есть helper переключения `fc-fan-ctrl`, но события формы
к нему не привязаны; кнопка сохранения вызывает отправку текущего объекта.
Axios экспортирован без прикладных baseURL/auth/interceptors. Стандартная
поддержка Basic/XSRF в библиотеке не доказывает отдельного требования токена.

Отдельно прочитаны оба getter: `/cgi-bin/luci/get_miner_conf.cgi` и
точный путь формы `/cgi-bin/get_miner_conf.cgi`. Они вернули одинаковые
значения в памяти и одинаковую полную схему из восьми ключей выше.
Равенство сохранено только как boolean; значения не экспортировались.
Это закрывает пробел чтения и соответствия **текущей формы**: в ней нет
переименования полей, весь прочитанный объект используется для записи.
Это не подтверждает старый `luci/...conf2` DTO.

Узкий программный контракт должен квалифицировать именно DG1+ с полной
сборкой `DG1+_SW_V1.0.4`, этой схемой и следующими оригинальными статическими
ответами (SHA-256 до обезличивания):

| Файл | SHA-256 |
| --- | --- |
| Основная HTML | `fa14fcfb892e357a336637905b69063d5693187865acc99208acdb56e54f2e87` |
| `/assets/index-575a0936.js` | `81704ae716ee6354865fd65cddd3bfde63bc8053efc48d18697e31106fd54cb7` |
| `/assets/Miner-f770af99.js` | `e5bda05b68bd26ae4a354feb7cf8423644631383d0345ef971b941c5cb770416` |

Незнакомая схема, неизвестные пароли и неподтверждённые статические файлы
не получают разрешение по одному имени модели. Прочие поля и нетронутые
слоты сохраняются целиком; тип integer режима нельзя преобразовывать в string.
Точный ack тела setter не наблюдался. HTTP 2xx сам по себе не подтверждает
принятие: программный контракт не должен заимствовать `stats=="success"`
из другой ветки. Свежий полный readback может подтвердить сохранённый конфиг,
но не принятие по ответу API, применение при добыче или постоянство после reboot.
Неопределённый результат не разрешает повторную запись.

Доказательства чтения и очищенные статические файлы:
локальный архив проверки.
`20261109T130304Z-05092c42/primary-config-comparison.json`, SHA-256
`a346010cdb13b2db332092920a2dafc21d529c019723e60b23906b595ed9ef5a`,
фиксирует равенство двух getter и наличие трёх паролей без их значений.
Полный [протокол](../testing/pool-read-elphapex-dg1plus-2026-11-09.md)
отделяет фактическое чтение, статический контракт и непроверенную аппаратную
запись. Результат не распространяется автоматически на DG1 и другие сборки.

## Программная реализация и проверка без записи

Реализован отдельный
[адаптер `elphapex.web.pools`](../../miner_scanner/elphapex_pool_backend.py).
Он использует текущие маршруты без `luci` для конфигурации/записи и LuCI
getter системной идентичности. Квалификация требует Elphapex/Stock,
профиль `elphapex.luci`, DG1+, полную сборку `DG1+_SW_V1.0.4`, точный
набор восьми верхних ключей и их типов, три объекта ровно `url/user/pass`
и все четыре оригинальных хеша выше. Новые поля или типы не получают
разрешение по сходству. Скрытые/неизвестные значения не заменяются пустыми.
Для проверенного основного интерфейса используется обычный профиль
HTTP Basic приложения; пароль доступа не становится паролем пула.

Тело строится копированием полного прочитанного объекта и заменой только
подготовленных слотов. Перед POST заново сверяются текущая идентичность,
конфигурация и статические файлы. Изменение после предпросмотра блокирует
запись. Известный MAC должен совпасть; отсутствие SN в проверенном системном
getter допустимо при совпавшем известном MAC, а противоречащий SN блокирует
операцию. Успешный HTTP-статус не объявляется доказанным ack: адаптер
возвращает `None` для 2xx. Общий механизм может подтвердить полный сохранённый
конфиг свежим чтением при неизвестном принятии по ответу API. При неопределённом
результате повторяются только чтения, без повторного POST, apply и reboot.

На текущем прочитанном конфиге подготовка `TEST.<IP>` и `TEST.<номер>`
проверена в памяти: в обеих ветках `ready=true`, в теле все восемь ключей,
изменения `url/user/pass`; нетронутые слоты, nonpool-значения и их типы
сохранены, исходный объект не изменён. `setter_called=false`;
audit прогона содержит только 15 GET. Артефакт:
`20261109T130833Z-337700f3/dry-run.json` в каталоге чтения,
SHA-256 `766efd9c0b02ecdee7a8ba41955dd38180a098658cd29303292dbd3bddf56902`.

Синтетический [fixture](../../tests/fixtures/elphapex_dg1plus_web_pools_read.json)
и [локальные тесты](../../tests/test_elphapex_pool_backend.py) проверяют
программный контракт. Реализация и подготовка в памяти не подтверждают
приём, сохранение, применение или последствия реальной записи на ASIC.

  `get_miner_conf`. Это mode-only материал другого семейства, а не доказательство

Обезличенный proof manifest с хешами, byte offsets и схемами сохранён в локальном архиве проверки.
Источники не изменены. Положительный fixture не создавался: ни один из этих
сохранённых материалов не закрывает пробел контракта записи пулов.
