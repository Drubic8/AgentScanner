# Совместимость управления Stock Antminer

## Что определяет доступные команды

С 01.10.2026 у L9, T21, S21 и вариантов S21+ / S21 Pro / S21 XP управление
может разрешаться по распознанному интерфейсу API независимо от даты прошивки.
Это дополняет точные аппаратно проверенные профили, не переносит на новые сборки
отметки о фактическом испытании оборудования.

С 02.10.2026 общие CGI-команды Stock/PitBit, включая KS5, распознаются по
булевому ответу API подсветки. Для Sleep/Wakeup дополнительно используется
однозначное соответствие модели и изученной схемы конфигурации. Подробная
[схема по семействам](control_api_compatibility.md) и
[проверка на оборудовании](../testing/family-controls-2026-10-02.md).

Два источника хранятся отдельно:

- `profiles/catalog.json`: идентификация, особенности телеметрии и
  `verified_commands` для конкретных испытанных сборок.
- `profiles/stock_interfaces.json`: изученные интерфейсы управления, формат
  записи конфигурации и набор режимов для моделей внутри каждого интерфейса.

`stock_compatibility.py` читает `/miner.html`, `/index.html`, по одному локальному
скрипту miner/index, и проверяет булевый ответ `/cgi-bin/get_blink_status.cgi`.
Содержимое скрипта сравнивается по SHA-256 с изученным вариантом. JavaScript
устройства не выполняется. Имя файла и дата прошивки не служат доказательством
совместимости. Ответы ограничены существующим размером и сроком опроса.

Изменение скрипта само по себе не блокирует общий CGI API. Для базовых режимов
Sleep/Wakeup при неизвестной странице все подходящие изученные схемы должны
дать одинаковый ключ режима, преобразование полей и значения команд. Если они
расходятся, запросы на устройстве не перебираются. Режимы Low/HEM требуют
изученного интерфейса или отдельного документированного профиля; специальные
режимы не выводятся из совпадения базовой конфигурации.

## Режимы зависят от интерфейса

| Изученный интерфейс | Модель | Режимы | Поле записи |
| --- | --- | --- | --- |
| miner.b91570 / miner.2a6d03 / miner.4dc679 | T21 | Normal 0, Sleep 1, HEM 2 | miner-mode |
| Те же страницы, ветка S21 | S21 / S21+ | Normal 0, Sleep 1, LowPower 3 | miner-mode |
| Те же страницы, ветка Pro / XP | S21 Pro / S21 XP | Normal 0, Sleep 1 | miner-mode |
| miner.c8af43 | S21+ | Normal 0, Sleep 1 | bitmain-work-mode |
| miner.05438c + изученная miner.html | S21+ | Normal 0, Sleep 1; HEM 2 / LEM 3 при соответствующих флагах API | bitmain-work-mode |
| miner.0ef2dc | L9 | Normal 0, Sleep 1 | miner-mode |
| miner.6b9cb7 + изученная miner.html | KS5 | Normal 0, Sleep 1 | miner-mode |
| miner.0fb1b6 + изученная miner.html без выбора режима | KS5 | Управление режимами не предоставлено страницей | — |

Список режимов воспроизводит изученные ветки кода интерфейса; упоминание режима
в переводах, имя модели или текущее значение режима сами по себе недостаточны.
Значение `bitmain-work-mode` при чтении сохраняет тип строки/числа конкретного API.
Профиль интерфейса определяет преобразование полей, например
`freq-level ← bitmain-freq-level`. Частоты и напряжения не подставляются константами.

### KS5: одинаковая конфигурация, разные возможности страницы

03.10.2026 запросами чтения изучены два Stock KS5:

- Файловая система `Wed Aug 28 11:12:11 CST 2024`: HTML содержит выбор режима,
  а `miner.6b9cb7.js` показывает его для KS5. Список — Normal 0 и Sleep 1.
- Файловая система `Mon May 13 11:55:33 CST 2024`: HTML не содержит выбора режима,
  хотя `miner.0fb1b6.js` включает неиспользуемые заготовки `modeNormal`/`modeSleep`
  и поле `miner-mode` в форме. Наличие этих строк не подтверждает доступность сна.

Обе сборки возвращают `bitmain-work-mode`, пулы, параметры вентиляторов, частоту,
напряжение и `bitmain-freq-level`. Для KS5 эта схема чтения сама по себе не
разрешает запись режима. В новых определениях `config_fallback: false` отключает
такой допуск, а `pages` требует известный SHA-256 HTML вместе с SHA-256 JavaScript.
Отпечаток HTML сохраняется в свидетельствах как `miner_page`; дополнительных
сетевых запросов для этого нет. Неизвестная, изменённая или недоступная страница
не разрешает режимы KS5, включая экспериментальный доступ. Общие CGI-команды
подсветки и перезагрузки продолжают определяться независимо.

Для интерфейса с выбором режима форма отправляет на `/cgi-bin/set_miner_conf.cgi`
пулы, текущие параметры вентилятора, `freq-level` и целевой `miner-mode`.
Частота и напряжение присутствуют только в ответе чтения и не добавляются в POST;
это соответствует изученной веб-форме. Пустые слоты пулов, отсутствующий пароль и
пользовательские настройки вентилятора сохраняются. Проверка читает
`bitmain-work-mode` с исходным строковым или числовым типом.

После изменения правила повторное чтение через ScannerService подтвердило
разные списки возможностей на этих двух устройствах. Сон, пробуждение и
перезагрузка на реальном оборудовании в этом исследовании не выполнялись;
`verified_commands` не расширялся. Формирование запросов, чтение результата,
отсутствие Low/HEM и отказ при смене страницы проверяются без сети в
`tests/test_ks5_modes.py`. Физическое засыпание и разгон требуют отдельной приёмки.

### S21+: режимы, объявляемые API

В интерфейсе `miner.05438c.js` список HEM/LEM зависит от булевых полей
`hem_mode` и `lem_mode` в `/cgi-bin/get_adjustment_params.cgi`. В каталоге
`mode_flags` связывает эти поля с действиями `hem` и `low`. Значения режимов
фиксированы изученным кодом: Normal 0, Sleep 1, HEM 2, LEM 3. Отсутствующий
ответ, строка `"true"` или число `1` не подтверждают дополнительный режим.
Normal/Sleep остаются доступными при совпадении HTML, JavaScript и полной схемы
конфигурации. Для этого интерфейса `config_fallback` выключен.

Дополнительный запрос выполняется только для распознанного интерфейса с
`mode_flags`; в свидетельствах сохраняются только названные булевы флаги.
Перед каждой командой повторная идентификация перечитывает их. Изменение флага
останавливает запись теперь недоступного режима.

Форма сохраняет `bitmain-chip-temp-threshold`, `bitmain-drop-freq-scale` и
`bitmain-power-off-delay` вместе с пулами, частотой, напряжением и параметрами
вентилятора. Неизвестное или отсутствующее обязательное поле блокирует запись.
На аппаратной проверке сборки `FR-1.40(260721-S21+)` 03.10.2026 оба флага были
`false`; Sleep/Wakeup прошли, полная конфигурация восстановлена. HEM/LEM на
реальном устройстве не отправлялись. Их условный допуск, изменение флагов и
сохранность настроек проверяются в `tests/test_stock_compatibility.py`.

### Старые страницы Locate и Reboot

Изученные `blink.html` используют form POST в `/cgi-bin/blink.cgi`:
`startBlink`, `stopBlink` и отдельное чтение `onPageLoaded`. Допуск требует
SHA-256 известной страницы и строго булевого `isBlinking`. Таймер 300 секунд
объявлен устройством; отсутствующий ответ не превращается в «LED выключен».
Каталог включает изученную страницу Z15e 2021 года.

`legacy_reboot` содержит отпечатки статических страниц, вызывающих GET
`/cgi-bin/reboot.cgi`, включая Z11 2019 и Z15e 2021. Чтение `reboot.html`
не выполняет перезагрузку. Отсутствие страницы Locate у старого Z11 оставляет
подсветку неподтверждённой; оно не доказывает отсутствие физического индикатора.

## Порядок выполнения

1. Сканирование определяет устройство и читает текущую конфигурацию.
2. Распознаётся интерфейс. Отпечатки кэшируются в памяти на `metadata_ttl`
   (по умолчанию 300 секунд), с привязкой к идентичности устройства.
3. Проверяется схема конфигурации: обязательные и разрешённые поля, тип режима,
   структура пулов. Неизвестное дополнительное поле блокирует запись режима до
   уточнения его роли. Пустые слоты пулов и отсутствующий пароль сохраняются как есть.
4. `Capabilities` передаются существующему меню GUI. Поддержка конкретного режима
   не выводится из названия модели. Установленный факт отсутствия режима блокирует
   его также в экспериментальном режиме.
5. Перед командой `force_identify=True` повторяет проверку устройства и интерфейса
   без кэша. Затем конфигурация перечитывается ещё раз непосредственно перед записью.
   Изменение её схемы или маски вместо секретов останавливают команду.
6. Выполняется одна запись и до трёх проверок целевого состояния. При таймауте
   записи допускается чтение, но автоматического повтора записи нет.
7. Для reboot сохраняется статус «принято, не подтверждено»: успех HTTP сам по себе
   не доказывает перезапуск. Восстановление хешрейта требует отдельного наблюдения.

Если страницу получить не удалось, общий API и конфигурация могут дать допуск
без неё. Сохраняется возможность использовать прежние документированные профили;
непроверенные команды по-прежнему требуют явного экспериментального режима.
Если изученный интерфейс прямо исключает действие, он блокирует его также при
наличии старой записи о проверке. Неизвестный скрипт не выключает совпадающий API.
Ошибка необязательного определения интерфейса не отбрасывает полученную телеметрию.

В `ControlCompatibility` сохраняются отпечатки, булевы флаги доступности и списки команд:
`compatible_commands` и `hardware_verified_commands`. Конфигурация, пароли и
токены туда не записываются. Совместимость не равна аппаратному испытанию.

## Добавление нового интерфейса

1. Снять только ответы чтения, страницу и её скрипт с согласованного устройства.
2. Изучить формирование JSON, соответствие полей чтения и записи, условные ветки
   выбора режимов и обработку ответа. Не запускать код устройства для анализа.
3. Добавить SHA-256 содержимого и описание в `stock_interfaces.json`; если контракт
   совпадает, использовать те же правила. Когда HTML меняет доступность режимов,
   указать также `pages` и запретить неоднозначный `config_fallback`, как для KS5.
   Не добавлять догадки по диапазону дат.
4. Добавить тесты отличий, отсутствующих режимов, сохранения настроек и смены
   схемы между проверкой и отправкой.
5. Аппаратные испытания проводить отдельно, записывая точную сборку в журнал.
   Запись в таблице испытаний не создаётся автоматически из совместимости API.

Проверки: `tests/test_stock_compatibility.py`. Реальное чтение описано в
[журнале](../testing/stock-api-compatibility-2026-10-01.md).
