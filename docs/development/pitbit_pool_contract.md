# PitBit C096: контракт пользовательских пулов

Основание — согласованное чтение одного ASIC **9 ноября 2026 года**
и независимый статический разбор его текущей формы. На оборудовании
подтверждены чтение и структура, без записи настроек. JavaScript
не исполнялся; код интерфейса в продукт не переносится.

## Точная область

Native VERSION подтвердил `Type=Antminer S21+_i`, `Miner=incm.C096`,
`API=3.1`, общий профиль `bitmain.pitbit`. HTTP-обёртка отображает
`Antminer S21+` и сборку `Tue May 10 16:20:00 CST 2020`.
Последняя не является источником версии движка и не должна служить
допуском по дате. `_i`, `+` и `incm.C096` нельзя выводить из похожего
Stock-названия или заменять старыми значениями C074/S21_i.

Штатный `drivers.make_record` без дополнительной телеметрии может записать
HTTP-сборку в `identity.firmware_version`, поскольку `VERSION.Miner`
не является его универсальным alias версии. Поэтому локальная проверка
кандидата допускает только `incm.C096` либо эту точную известную HTTP-строку
при совпавших модели `_i`, API и профиле. Это допуск к дальнейшему чтению,
не подтверждение движка и не готовый план. Безусловный свежий native
Type/Miner/API и положительный STATUS остаются обязательными до подготовки,
перед POST и при readback. Драйвер и C074-профиль для этого не менялись.

Этот контракт относится к данному сочетанию native-идентичности,
схемы и статических файлов. Он не означает поддержку всех PitBit,
всех C096, соседних моделей или только совпавшей HTTP-страницы.
Известные раньше LED/Sleep/Reboot C074 и сохранённый mode-only лог
не являются доказательствами настройки пулов.

## Фактический read-to-write map

| Этап | Точное поведение текущей формы |
| --- | --- |
| Базовый origin | `window.location.origin` |
| Чтение | `GET /cgi-bin/get_miner_conf.cgi`, `Cache-Control: no-cache` |
| Состояние | Весь JSON становится `minerConfState` |
| Пользовательская форма | Редактирует `url/user/pass` исходных объектов `pools` |
| Сохранение | `POST /cgi-bin/set_miner_conf.cgi`, JSON `{...minerConfState, pools: editedPools}` |
| Сериализация | `Content-Type: application/json`, один `JSON.stringify` |
| Ожидаемый ack | HTTP `ok` и строковое `stats == "success"` |
| Отдельный известный отказ | `stats == "error"`, `code == "M028"`, `msg == "firmware upgrade process"` |

Форма не строит Stock DTO, не переименовывает ключи и не добавляет
значения по умолчанию. Весь остальной конфиг передаётся без преобразований.
Программный адаптер должен копировать объект глубоко: особенности shared
state React-формы не должны позволять менять снимок предпросмотра при
редактировании нового тела.

Получены ровно 23 верхних поля:

| Ключи | Тип |
| --- | --- |
| `pools`, `poolshotelfee` | array |
| `api-listen`, `api-network`, `bitmain-fan-ctrl`, `bitmain-use-vil`, `enable_working_voltage`, `need_update_fw_now`, `target-temp-ctrl` | boolean |
| `bitmain-work-mode` | integer |
| `api-allow`, `api-groups`, `bitmain-ccdelay`, `bitmain-fan-pwm`, `bitmain-freq`, `bitmain-freq-level`, `bitmain-hashrate-percent`, `bitmain-pwth`, `bitmain-voltage`, `freq_mode`, `hotelfeepercent`, `target-temp`, `working_voltage` | string |

`pools` — три объекта ровно с integer `index` и string `url/user/pass`.
В наблюдавшемся порядке индексы `[0, 1, 2]`, все три пароля присутствуют.
Канонические пользовательские слоты не должны терять эти индексы:
в полный исходный объект переносятся только изменяемые строки.
Тип integer режима сохраняется, частоты/вентилятор/температуры/напряжение
не преобразуются и не подменяются.

## Служебные пулы и потенциальное действие

`poolshotelfee` — отдельный список из одного объекта ровно со строковыми
`url/user/pass`, без индекса; все три значения присутствуют.
Этот список не добавляется к трём пользовательским слотам, не проходит
через замену worker и сохраняется целиком вместе с `hotelfeepercent`.
Отдельная форма hotel fee преобразует процент, но форма пользовательских
пулов этого не делает. Скрытая вкладка не означает отсутствия этих данных.

В текущем конфиге `need_update_fw_now` имеет точный boolean `false`.
В bundle нет обращения к имени этого ключа: полный spread переносит его
в POST автоматически. Серверная семантика поля не доказана.
Безопасная реализация должна блокировать `true`, пропуск и другой тип,
не изменять флаг ради допуска и повторно проверять его перед записью.
Это сохраняет текущий объект, не разрешая непроверенный запрос обновления.

## Проверки и подтверждение результата

Перед записью необходимы свежие native VERSION, идентичность, точная
схема всех 23 полей и вложенных массивов, отсутствие неизвестной схемы
и пересылаемых скрытых полей пулов, а также совпадение текущих HTML
и bundle. Native VERSION должен иметь непустой список `STATUS` только
со статусами `S`. Конфликт с замороженным
предпросмотром блокирует POST. Профиль доступа берётся обычным способом
из приложения; значение пароля API не используется как пароль пула.

Строка `stats=="success"` при HTTP `ok` — ack, установленный по коду формы,
а не фактически наблюдавшийся ответ setter. Явный отказ не становится
неопределённым успехом; неизвестное тело/обрыв остаются непроверенными.
После единственного POST нужен свежий полный конфиг: сравниваются
ожидаемые пользовательские поля и неизменность всех остальных данных,
включая индексы и служебные пулы. При неопределённом результате
разрешены только повторные чтения, без повторного POST.

Frontend после ack показывает статус; общий provider читает конфиг
периодически, обработчик сохранения не ожидает независимого readback.
Отдельного apply/reboot в нём нет. Это не доказывает отсутствие
серверного перезапуска и не подтверждает применение при добыче.
Аппаратные приём, сохранение и применение записи остаются непроверенными.

## Реализация

Добавлен [отдельный адаптер](../../miner_scanner/pitbit_pool_backend.py)
`pitbit.c096.web.pools` с перечисленными точными условиями допуска.
Он проверяет native-движок отдельно от HTTP-обёртки, сохраняет исходные
индексы при изменении канонических пользовательских слотов и делает
глубокую копию всего конфига. Служебный пул, комиссия, режимы, температуры,
охлаждение и напряжения не проходят преобразование.

Перед POST выполняется новое чтение состояния и сравнение с предпросмотром;
явный отказ возвращает `False`, разобранный успешный ack — `True`,
неизвестный ответ — `None`. Общий механизм подтверждает результат только
свежим полным readback. Никаких дополнительных setter, apply/reboot,
альтернативного формата или повторной записи нет. Маски проверяются
в пользовательских/служебном пулах; допустимые ACL wildcard не являются
паролями и сохраняются как прочитаны.

Синтетический [пример ответа](../../tests/fixtures/pitbit_c096_pools_read.json)
и [локальные сценарии](../../tests/test_pitbit_pool_backend.py) отделены
от аппаратной проверки. Их наличие не означает, что реальное устройство
приняло или применило записанные настройки.
Отдельный сценарий создаёт запись через настоящий `make_record` из native
VERSION и HTTP system, без optional stats и ручной подмены версии.
Одна и та же HTTP-дата не разрешает свежий C074; C096 проходит полный
путь на имитаторе с сохранением всего конфига, индексов и hotel pool.

Финальная подготовка адаптером на прочитанной конфигурации со штатным
`make_record`, без ручной подмены FW/API, прошла
без записи: суффиксы IP и номера дали `ready=true`, изменения
`url/user/pass`, все 23 ключа тела; сохранены 22 остальных поля и типы,
нетронутые слоты, индексы, hotel pool/комиссия и `false` флага обновления.
Исходный объект не изменён; все проверки `true`, `setter_called=false`.
Backend/source экспорта — `pitbit.c096.web.pools` / `pitbit.web.conf`.
Audit финального прогона: 9 HTTP GET и 2 native `version`, никаких POST.
Каталог `20261109T140333Z-a3828efd` в `live-pitbit-c096-read`;
`dry-run.json`, `request-audit.json`, `compatibility.json`,
`identity-sources.json`. Версия записи — естественная HTTP-дата,
а native-источник отдельно подтверждает C096; candidate и авторитетный
источник версии не смешиваются.
Это положительный результат подготовки в памяти, без проверки аппаратных
приёма, сохранения или применения записи.
