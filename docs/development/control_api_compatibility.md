# Совместимость управления по семействам API

Актуальная схема с 02.10.2026. Версия прошивки записывается в идентичность и
историю проверки устройства. Новая дата или изменённая веб-страница сами по
себе не отключают общие команды при совпадающем API.

## Правила выбора

| Семейство | Общие команды и основание | Дополнительные режимы |
| --- | --- | --- |
| Bitmain Stock / PitBit | Подсветка JSON `blink`, перезагрузка CGI; идентифицированное семейство и булевый `get_blink_status.cgi` | Для Stock Sleep/Wakeup — изученная схема конфигурации с однозначным преобразованием в запись; Low/HEM — изученный интерфейс или прежняя аппаратная проверка |
| Elphapex DG1 / DG1+ | Подсветка и перезагрузка LuCI; булевый `get_blink_status.cgi`. Sleep/Wakeup дополнительно требуют `fc-work-mode` 0 / −1000 | Low/High автоматически не добавляются |
| VNish | Локальный OpenAPI объявляет POST-операции. Подсветка выбирает `find-miner/on` или `locate-miner/is_enabled`; чтение `find_miner` должно быть булевым | Неизвестные схемы и обязательные параметры не подставляются |
| WhatsMiner | Документированный RPC 3.0, длина кадра и авторизация, включённый API Write | Разрешение записи проверяется отдельно от обнаружения ASIC |
| Avalon | Семейство Universal API и чтение состояния LED | Питание зависит от изученного контракта серии; совместимость LED не расширяет режимы питания |

## Stock: конфигурация и разные интерфейсы

Распознанный интерфейс `miner` остаётся предпочтительным источником полного
набора режимов. При неизвестном или отсутствующем интерфейсе сканер сопоставляет
модель и текущую конфигурацию с уже изученными контрактами в
`profiles/stock_interfaces.json`.

Для базовых Sleep/Wakeup необходимо, чтобы **все подходящие контракты совпали**
по ключу записи режима, соответствию полей конфигурации и значениям команд.
Два возможных разных запроса не перебираются на устройстве. Неизвестные поля,
неполная схема или отсутствие подходящей модели не создают новый допуск.
Совпадение базового контракта не доказывает наличие Low, High или HEM.

Документированные профили сохраняются как дополнительное основание; ранее
непроверенные правила остаются непроверенными и требуют явного экспериментального
режима. Они не становятся подтверждёнными из-за совпадения базовой конфигурации.
Если изученный интерфейс прямо исключает режим, это ограничение имеет приоритет.
Перед записью конфигурация перечитывается, схема проверяется повторно, пулы,
пароли, параметры вентиляторов и настройки частот сохраняются.

## VNish: описание API вместо скрипта страницы

Читаются фиксированные `/api/v1/status` и `/docs/api-doc.json`. Из описания
используются только известные локальные пути и изученные формы данных.
Внешние URL из `servers` и `$ref` не запрашиваются; локальные ссылки разрешаются
с ограничением глубины. Документация не задаёт произвольные команды программе.

Новый интерфейс может одновременно объявлять `locate-miner` и устаревший
`find-miner`: предпочтение получает `locate-miner`. Если `requestBody` описан,
он должен совпадать с известным форматом. У некоторых выпущенных версий это
описание пропущено; формат установлен прежними исследованиями и испытаниями.

Sleep/Wakeup/Reboot разрешаются только при объявленной известной POST-операции,
которая не требует нового обязательного тела запроса. При недоступном OpenAPI
сохраняется запасной способ распознавания подсветки по ранее изученному скрипту.
Явно неизвестное описание API не перекрывается старым отпечатком страницы.

## Исполнение и результаты

Перед командой повторно проверяются устройство, текущая идентичность и API.
Запись выполняется один раз, затем читается целевое состояние. Потеря ответа не
вызывает повторную отправку. Идентификатор команды защищает от повторной записи.

`supported` означает распознанный контракт; `hardware_verified_commands`
описывает отдельные аппаратные испытания. Приём команды без подтверждения
остаётся `unconfirmed`, включая перезагрузку. Подтверждённый режим пробуждения
не равен восстановлению хешрейта — для этого требуется дальнейший мониторинг.

Новая модель или действительно другой API добавляются в соответствующий
модуль семейства с регрессионными проверками. Для нового оформления страницы
при прежнем базовом API правило отдельной даты прошивки не требуется.

Основные модули: `stock_compatibility.py`, `elphapex_compatibility.py`,
`vnish_compatibility.py`, `whatsminer_compatibility.py`, `avalon_compatibility.py`.
Диспетчер, журнал и проверка результата находятся в `commands.py`.
