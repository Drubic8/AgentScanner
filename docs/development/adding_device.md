# Как добавить прошивку или устройство

## 1. Сначала получить факты

Определите точную модель, ревизию, строку прошивки, версию API, доступные запросы чтения и единицы. Сохраните обезличенные ответы в `tests/fixtures/`. Удалите пароли, токены, личные имена workers и внутренние адреса. Укажите происхождение: настоящий аппаратный ответ или синтетический пример.

Начните с [каталога профилей](../../miner_scanner/profiles/catalog.json), [реестра](../../miner_scanner/profiles/__init__.py), [драйверов](../../miner_scanner/drivers.py) и [контрактов](../../miner_scanner/models.py). Не добавляйте выбор производителя в GUI, `core.py` или общий сервис команд.

## 2. Новая версия существующего API

Добавьте профиль с уникальными `id` и `version`. Скопируйте план `queries` ближайшего семейства и задайте более высокий `priority` и точные ограничения `match.models`, `match.firmware_versions`, при необходимости `match.api_versions`.

Каждый запрос — массив:

```json
["имя_ответа", "http", "/путь/чтения", true, {"port": 80}]
```

Последний объект необязателен. `true` означает, что **весь ответ** можно кэшировать на интервал метаданных. Если ответ содержит состояние майнинга или оперативные ошибки, используйте `false`. Протоколы: `cgminer`, `rpc`, `http`, `http_post`, `html`, `text`. Для RPC параметр записывается после двоеточия, например `get.miner.status:summary`.

`http_post` допустим только для документированного запроса чтения: HTTP-метод сам по себе не доказывает безопасность. Планы обнаружения и мониторинга не должны содержать управляющие запросы.

Существующие сигнатуры описаны в `signatures()`. Семейные профили чтения могут иметь широкую применимость; подтверждённое управление требует точных моделей и версий. При равных приоритетах либо конфликте производителей профиль не выбирается. Не исправляйте такой конфликт произвольным порядком файлов.

## 3. Явные метрики

Если новая прошивка меняет название поля или единицу, добавьте `metrics`. Пример формы (путь и единицу нужно заменить на подтверждённые):

```json
{
  "rate": {"path": ["ответ", "объект", "поле"], "unit": "TH/s"},
  "average_rate": {"path": ["ответ", "объект", "среднее"], "unit": "TH/s"}
}
```

Элементы пути — ключи словаря или числовые индексы массива. Нет `eval`, выражений Python или shell. Отсутствующий путь даёт неизвестное значение, не ноль. Размерности текущего и среднего значений должны совпадать.

Для резервных источников той же размерности можно задать `fallback_paths` —
список путей после основного `path`. Используется первое корректное неотрицательное
число, включая ноль. Например, профиль `bitmain.stock.z11.20190423` читает
`GHS 5s` из SUMMARY, затем из STATS; оба значения этой сборки выражены в kSol/s.
Это правило нельзя переносить на все Z11: октябрьская сборка возвращает Sol/s.
`match.compile_times` сопоставляет точное поле CGMiner `CompileTime` и позволяет
выбрать правило телеметрии без HTTP-аутентификации. Для подтверждённых команд
по-прежнему обязательны ограничения `models` и `firmware_versions`.

## 4. Команды в рамках HTTP API

`command_rules` позволяет задать действие без изменения общего диспетчера. Пример структуры **не является реальной командой ASIC**:

```json
{
  "low": {
    "method": "POST",
    "path": "/example/set-mode",
    "payload": {"mode": "low"},
    "verify": {
      "path": "/example/read-mode",
      "field": ["mode"],
      "equals": "low"
    }
  }
}
```

Если API требует полную конфигурацию, `read_config` задаёт путь чтения: указанная `payload` накладывается на исходные поля. Конфигурация с масками вместо секретов отклоняется. Тип ожидаемого значения проверки учитывается: число `1` и строка `"1"` различаются.

Если имена полей чтения и записи различаются, добавьте `config_fields` — словарь
`"поле записи": "поле чтения"`. В этом случае в запрос копируются только перечисленные
поля, затем применяется `payload`. Отсутствие любого исходного поля останавливает
запись. Пример подтверждённого соответствия для Stock L9 от 10.02.2025:
`"freq-level": "bitmain-freq-level"`; `"miner-mode": 0` задаётся в `payload`,
а проверяется `"field": ["bitmain-work-mode"], "equals": "0"`.

При сетевой ошибке записи декларативная команда пытается прочитать целевое
состояние без повторной отправки. Подтверждённое состояние даёт `succeeded`,
но `accepted_by_api` остаётся `false`, если ответ на саму запись не получен.

Если конкретная прошивка возвращает другой успешный код, укажите `success_codes`
в правиле команды. Это непустой список строк или целых чисел, применяемый только
к этой команде. Например, Stock L9 от 10.02.2025 возвращает `B100` при выключении
подсветки. Допустимый код не заменяет проверку фактического состояния через `verify`.

Идентификаторы действий: `identify_on`, `identify_off`, `reboot`, `mining_stop`, `mining_start`, `low`, `normal_power`, `hem`. `normal_power` меняет мощность; `mining_start` возобновляет вычисления. Не объединяйте эти действия.

Список `verified_commands` оставляйте пустым до проверки конкретной модели/версии на оборудовании. Для аппаратного испытания существует явно включаемый режим совместимости; он не считается доказательством проверки. После испытаний добавьте протокол результата, точные ограничения `match` и только действительно подтверждённые действия.

У Stock L9/T21/S21 действует также [распознавание интерфейса управления](stock_api_compatibility.md).
Совместимые команды разрешаются независимо от даты сборки, но не добавляются
автоматически в `verified_commands`. Для разных наборов режимов одной модели
добавляйте отдельные контракты интерфейса в `stock_interfaces.json`.

Рабочий синтетический пример добавления режима находится в `test_new_power_mode_needs_only_a_profile_rule` в [tests/test_scanner.py](../../tests/test_scanner.py). Он проверяет расширение механизма, а не аппаратную совместимость.

## 5. Новый протокол или сложный сценарий

Добавьте транспортный метод или драйвер с ограничением времени и размера ответов. Добавьте чистый парсер в `parsers/` и зарегистрируйте его в `drivers.PARSERS`. Для нового сложного управления добавьте исполнитель в `commands.EXECUTORS` и его возможности в `SUPPORTED_ACTIONS`. GUI не меняется.

Новая сигнатура обнаружения должна опираться на структуру ответа и идентификационные поля. Порт, текст worker, пул или сообщение об ошибке не доказывают производителя. Не добавляйте автоматический перебор паролей, управляющих endpoint или нескольких несовместимых payload.

## 6. Обязательные проверки

- Правильное определение и близкая несовместимая версия.
- Конфликт профилей и другой производитель с похожими данными.
- Неполный ответ, отсутствие полей, ноль и явные единицы измерения.
- Точный тип payload и сохранение посторонних полей конфигурации.
- HTTP 200 без изменения состояния, отказ авторизации, таймаут.
- Отсутствие автоматического повтора неидемпотентной команды.
- Смена прошивки/оборудования после сохранения паспорта.

Запуск: `python scripts/check_scanner.py`. Тесты должны обходиться без ASIC и доступа к интернету. Аппаратное подтверждение оформляется отдельно.
