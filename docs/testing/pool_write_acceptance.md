# Приёмка изменения пулов, workers и паролей пулов

Дата плана: **2026-11-16**. Выполнен узкий одиночный пилот:
[S21+ Stock FR-1.15 — worker третьего слота](pool-write-s21plus-worker-2026-11-16.md).
Остальные поля и контракты сохраняют статус непроверенных аппаратной записью.
Разрешение на этот пилот не распространяется на другие записи или устройства.
Этот план готовит дальнейшую приёмку; конкретная запись, окно работ
и восстановление исходных настроек согласуются отдельно после заполнения
параметров ниже. Адреса, новые пулы и пароли здесь не назначаются.

## Что должно быть определено до согласования записи

| Поле плана | Что зафиксировать |
| --- | --- |
| Цель | Выбранный ASIC, его псевдоним, точные модель/FW/API и распознанный контракт; версия программы |
| Изменение | Слоты, новый URL, общее имя до точки, способ суффикса и пароли отправляемых слотов; точный предпросмотр |
| Исходное состояние | Все слоты и непуловые настройки, доступные исходные пароли для восстановления; ожидаемые неизменные поля |
| Наблюдение | Окно работ, срок ожидания применения/валидных шар и способ проверки на стороне пула |
| Восстановление | Исходные значения, ответственный оператор и согласованный порядок отката; допустимость apply/reboot |

Полные настройки и секреты остаются в защищённом рабочем контексте оператора,
не в Git, журнале или этом протоколе. Если данных для восстановления нет,
аппаратный пилот не начинают. В отчёт попадают псевдонимы, версии, имена/типы
полей и результаты сравнений без IP, MAC/SN, URL, workers и паролей.

## 1. Проверки без оборудования

Перед пилотом сверить штатные проверки ядра (`scripts/check_scanner.py`)
и GUI из [CONTRIBUTING.md](../../CONTRIBUTING.md). Положительные сценарии:
URL-only, worker-only с суффиксом IP/номера, password-only; сохранение двух
нетронутых слотов, всех непуловых значений и их типов. Запись устройства
должна формироваться обычным сборщиком без ручной подмены версии/модели.

Сначала на имитаторах проверить отказы: чужие FW/API/хеши или схема;
неизвестные и прочитанные маски паролей; изменение идентичности/конфига
после предпросмотра; отрицательный/неизвестный ack и несовпавший readback;
коллизии workers, дубликат команды, отмена и частичный отказ группы.
Явно введённые пустые/литеральные пароли проверяются отдельно от масок чтения.
Отказ до отправки означает ноль setter; таймаут после отправки — максимум
один setter без автоматического повтора и воспроизведения из журнала.

## 2. Одиночный пилот

Выбрать **один ASIC на каждый точный проверяемый контракт**. Успех одной
Stock-формы не сертифицирует другие модели, схемы и версии.
На этом ASIC подготовить отдельные планы для изменения URL, worker по IP,
worker по порядковому номеру и пароля пула. Перед каждой операцией заново
прочитать состояние и просмотреть фиксированный план.

После каждой однократной записи раздельно зафиксировать:

- ответ API и свежий конфиг: выбранные поля совпали, остальные слоты,
  индексы, режим, охлаждение, частоты/напряжения и служебные поля сохранены;
- фактический результат: ASIC подключился к назначенному пулу, тот видит
  ожидаемый worker и валидные шары; добыча восстановилась в назначенное окно;
- восстановление исходных значений по согласованному плану и его проверку.

HTTP 2xx, ack или совпавший runtime worker не заменяют все эти результаты.
Сохранение после reboot проверяется только если это действие включено
в согласованное окно; до такой проверки постоянство после перезапуска
остаётся непроверенным. При расхождении остановить новые отправки, сохранить
обезличенный результат и выполнить согласованное восстановление через новый
план, без слепого повторения неопределённой команды.

### Особенности контрактов

| Ветка | Дополнительное условие приёмки |
| --- | --- |
| Stock | Совпадают изученные карта/схема/страница. Проверить точные поля записи и тип текущего режима; приёмка пулов не разрешает менять питание |
| VNish | Совпадают текущие OpenAPI settings и схема. Отдельно учитывать `restart_required`/`reboot_required`; чтение сохранённого settings не доказывает применение, несогласованный apply/reboot не выполнять |
| WhatsMiner RPC3 | Проверить реальный RPC3, API Write и права аккаунта, явно задать пароли всех трёх слотов, автоматический суффикс пустой. Приём выбранного AES/PKCS7 конкретной FW ещё нужно подтвердить. Runtime-only результат программы остаётся `unconfirmed`; сохранение паролей подтверждается отдельно, работа пула его не доказывает |
| DG1+ | Только изученный V1.0.4, восемь полей и четыре статических хеша. HTTP 2xx не доказывает ack; нужен полный saved-config readback и фактическая проверка пула |
| PitBit C096 | Свежие native S21+_i / C096 / API 3.1, точные интерфейс и 23 поля; HTTP-дата лишь кандидат. `need_update_fw_now=false`; индексы, hotel pool и комиссия остаются неизменными |

Подробные ограничения: [общая матрица](../development/pool_configuration.md),
[WhatsMiner](../development/whatsminer_pool_contract.md),
[DG1+](../development/elphapex_pool_contract.md),
[PitBit C096](../development/pitbit_pool_contract.md).

## 3. Небольшая группа и допуск к эксплуатации

После успешного одиночного пилота выбрать 2–3 устройства с тем же
подтверждённым контрактом. Проверить единое имя до точки, уникальность
суффиксов, устойчивую нумерацию и отдельный результат каждого ASIC.
Отмена останавливает новые отправки, но не отменяет уже отправленные;
частичный отказ не вызывает повторов успешных/неопределённых команд.

В протоколе отдельно отметить: ack, сохранённую конфигурацию, работу пула,
сохранность остальных настроек, постоянство после reboot и восстановление.
Недоказанный пункт остаётся «Не проверено», для WhatsMiner сохраняется
ограничение runtime-подтверждения. Допуск выдаётся точному сочетанию
модели/FW/API/контракта после оценки этих результатов, затем выполняется
постепенное развёртывание. Новые схемы и прошивки проходят собственную приёмку.
