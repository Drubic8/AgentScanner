# Avalon 1346-110: подсветка, Sleep и Wakeup

Проверено 02.10.2026 на `10.33.213.13` после отключения пользователем
первоначального адреса `10.33.213.11`.
Модель: `1346-110`, API `3.7`, SWTYPE `MM317`, HWTYPE `MM4v1_X3`,
сборка `24041001_08b0955_0196aba`.

## Выполнено

До исправления Avalon имел только действие `identify_toggle`; обычные GUI-команды
`led_on`/`led_off` отсутствовали в реализации. Добавлены отдельные действия
с проверкой описанного Canaan LED API на устройстве.

| Действие | Команда TCP 4028 | Результат |
| --- | --- | --- |
| Чтение | `ascset\|0,led,1-255` | `STATUS=I, Code=118, LED[0]` |
| Включение | `ascset\|0,led,1-1` | `STATUS=S, Code=119`; чтение подтвердило `LED[1]` |
| Выключение | `ascset\|0,led,1-0` | `STATUS=S, Code=119`; чтение подтвердило `LED[0]` |

Управление проверено через общий `execute_command`, результат обеих команд
`succeeded`. Подсветка оставлена выключенной. Визуальная проверка не получена.
Результаты последующей проверки Sleep/Wakeup приведены ниже.

Распознавание ограничено структурированными данными Avalon, API 3.7,
одним подключённым модулем и успешным ответом запроса состояния LED.
Дата прошивки не является условием разрешения подсветки.
Неоднозначный ответ и несколько модулей блокируют LED-команды.
При потере ответа на запись команда не повторяется: результат проверяется чтением.

## Запись Sleep/Wakeup

Руководства [A10](https://github.com/Canaan-Creative/avalon10-docs/blob/master/Universal%20API/Avalon%20A10%20API%20manual-EN.md)
и [Q](https://www.canaan.io/resource/api/avalon-q-commands) описывают разные
способы остановки/запуска. Пользователь предоставил `Avalon.pcapng` из FMS 3.3.4
и подтвердил последовательность кнопок: Sleep → повторное сканирование → Wakeup.

| Кадр / время | Запрос | Ответ |
| --- | --- | --- |
| 4 / 0,015 с | `ascset\|0,softoff` | `S`, код 119, `ASC 0 set OK` |
| 13 / 9,930 с | `estats` | `In Idle`, `GHSspd[0.00]`, `PS[0 1197 0 0 0 1393 11]`, `SoftOFF[6]` |
| 52 / 17,351 с | `ascset\|0,reboot,1` | `S`, код 119, `ASC 0 set OK` |

Таким образом, Wakeup у этой серии реализован перезагрузкой. После захвата
отдельное чтение устройства подтвердило `In Work`, `SoftOFF[0]`, 110,78 TH/s.
Обезличенная выдержка находится в `tests/fixtures/avalon_1346_fms.json`;
адреса пулов, воркеры, DNA/MAC из исходного захвата в неё не включены.

При первом чтении после включения ASIC сообщал `SoftOFF[6]`, `In Idle`,
хешрейт 0. Поэтому любой ненулевой `SoftOFF` нельзя автоматически считать
подтверждением команды Sleep.

## Реализация и проверка через сканер

Контракт разрешается по модели 1346-110, API 3.7, HWTYPE MM4v1_X3,
SWTYPE MM317, одному модулю и структуре телеметрии. Дата сборки не ограничивает
совместимость, но фактические испытания относятся к указанной в начале сборке.
Для других серий нужен отдельный подтверждённый контракт.

Первый цикл `execute_command`: оба запроса приняты API. За первоначальные
три короткие проверки переход не успел подтвердиться (`unconfirmed`).
Последующее чтение показало uptime 23 с вместо 600 с перед циклом,
`SoftOFF[0]`, `In Work`, питание плат включено: перезагрузка выполнена.
После этого интервал чтения состояния увеличен; отправка команд не повторяется.

Перед следующим циклом устройство вернулось к майнингу: uptime 181 с,
87,59 TH/s, `In Work`, `SoftOFF[0]`. Во втором цикле Sleep на uptime 211 с
перевёл его в `In Idle`, `SoftOFF[5]`, текущий хешрейт 0; на uptime 220 с
питание плат показало `PS[0 1199 1 0 0 1393 11]` (нулевые ток и мощность).
Такое состояние сохранялось при последующих чтениях. Изначальная проверка
требовала также строго нулевого напряжения и оставила результат `unconfirmed`.
Она исправлена с учётом реально полученных 0/1 единиц напряжения;
нулевые ток и мощность остаются обязательными. Случай покрыт отдельным тестом.
Повторный Wakeup принят API; подтверждение перезапуска проверяется отдельно
от окончания разгона. После исправления порога новый цикл команд не выполнялся.
Итоговое чтение после второго Wakeup: uptime 145 с, `In Work`, `SoftOFF[0]`,
29,29 TH/s. Устройство оставлено майнить, разгон до номинала не проверялся.

Сон проверяется переходом из работы в Idle, нулём текущего хешрейта
и отключением питания плат. Пробуждение/перезагрузка — сбросом uptime.
Если ASIC уже был в Idle, приём Sleep сам по себе не считается подтверждённым
переходом. Один `SoftOFF[6]` не подтверждает состояние «Сон».

Тесты `tests/test_avalon_commands.py`: отдельные on/off/toggle,
блокировка некорректного чтения, запрет неоднозначной адресации модулей,
проверка состояния после потери ответа, отсутствие повторной записи;
также команды из захвата FMS, переходы питания, сброс uptime,
отказ API, чужой интерфейс, изменение прошивки и неоднозначная телеметрия.
EXE не пересобирался.
Локальная проверка: `python -m unittest discover -s tests -q` — 208 тестов прошли.

## Исправление состояния после пользовательского Sleep

При следующей проверке пользователь сообщил «Работает» с остаточными
0,01 TH/s в GUI. Чтение только API показало `SoftOFF[5]`, `In Idle`,
`GHSspd[0.00]`, `GHSmm[0.00]`, `PS[0 1198 0 0 0 1393 11]`.
При этом `SUMMARY.MHS 1m` ещё содержал 1102,8 MH/s, а средний за время работы
хешрейт — 22622399,47 MH/s. Причина — приоритет минутного среднего и
вывод состояния по любому положительному хешрейту.

Теперь текущий хешрейт имеет приоритет над минутным средним. Состояния
`Sleep` / `Stopping` определяются по проверенной телеметрии 1346/MM317;
средний хешрейт сохраняется отдельно. `SoftOFF[6]` при запуске остаётся
неоднозначным. Повторный `ScannerService.poll` на этом же устройстве подтвердил
`Status=Sleep`, `mining_state=stopped`, `Real=0.00 TH/s`.
Команды управления при этой проверке не отправлялись.

Добавлены семь тестов телеметрии, общий набор — **215 тестов, все прошли**.
Отдельно проверены подписи состояний Windows, фильтр «Засыпает» и смена темы
через Qt offscreen на демонстрационных данных. Android получил подписи
переходов; новая APK-сборка и проверка на телефоне в эту проверку не входили.
