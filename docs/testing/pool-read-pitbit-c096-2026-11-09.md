# PitBit C096 / S21+_i: чтение конфигурации пулов, 09.11.2026

Проверен один выбранный пользователем ASIC в согласованной области
только чтения. Native VERSION подтвердил `Type=Antminer S21+_i`,
`Miner=incm.C096`, `API=3.1`; профиль — `bitmain.pitbit`.
HTTP-обёртка сообщает `Antminer S21+` и сборку
`Tue May 10 16:20:00 CST 2020`. Эта строка шаблона не заменяет
версию движка C096 и не служит допуском к записи по дате.
Старый mode-only контракт S21_i/C074 и карты Stock не переносились.

При отсутствии дополнительной телеметрии штатный `drivers.make_record`
может сохранить в `identity.firmware_version` именно сборку HTTP-обёртки:
поле native `Miner` не является его универсальным alias версии.
Узкий адаптер допускает `incm.C096` либо эту точную HTTP-строку только
как кандидата к дальнейшему чтению. Готовность и запись всё равно требуют
свежий native `Miner=incm.C096`, `Type=Antminer S21+_i`, `API=3.1`
и весь набор остальных проверок. По одной HTTP-дате готового плана нет.

IP, MAC/SN, значения пулов, workers, паролей, комиссии и настроек
в документ не включены. Native-запрос был только `version`;
первичный прогон содержит один native `version`, 5 HTTP GET и 0 POST.
Более поздняя подготовка адаптером описана отдельно ниже.
JavaScript не исполнялся.

## Полученная схема

`GET /cgi-bin/get_miner_conf.cgi` вернул 23 верхних поля:

| Ключи | Тип |
| --- | --- |
| `pools`, `poolshotelfee` | array |
| `api-listen`, `api-network`, `bitmain-fan-ctrl`, `bitmain-use-vil`, `enable_working_voltage`, `need_update_fw_now`, `target-temp-ctrl` | boolean |
| `bitmain-work-mode` | integer |
| `api-allow`, `api-groups`, `bitmain-ccdelay`, `bitmain-fan-pwm`, `bitmain-freq`, `bitmain-freq-level`, `bitmain-hashrate-percent`, `bitmain-pwth`, `bitmain-voltage`, `freq_mode`, `hotelfeepercent`, `target-temp`, `working_voltage` | string |

`pools` содержит три пользовательских объекта, в каждом присутствуют
строковые `url`, `user`, `pass` и целочисленный `index`.
Все три пароля присутствуют. Отдельная схема подтвердила исходные
индексы `[0, 1, 2]`; их нельзя пересоздавать по догадке или терять
при преобразовании в канонические слоты.
`poolshotelfee` — самостоятельный служебный список; он не является
четвёртым пользовательским пулом. Прочитан один служебный объект
ровно со строковыми `url/user/pass`, все три присутствуют, индекса нет.
Его содержимое и `hotelfeepercent`
не должны изменяться при редактировании пользовательских пулов.

Sidecar подтверждает наличие служебного списка даже там, где общий
обезличенный экспорт не выводит его вложенную схему. Отсутствие поля
в ограниченном экспорте не означает его отсутствия в ответе устройства.

## Текущая форма

Основная HTML загружает React bundle `/static/js/main.b3210ed9.js`.
Статический разбор установил:

| Шаг | Точное поведение |
| --- | --- |
| Origin | `window.location.origin` |
| Чтение | `GET /cgi-bin/get_miner_conf.cgi`, `Cache-Control: no-cache`; JSON становится полным `minerConfState` |
| Пользовательские пулы | Отдельное состояние `pools`; редактируются свойства существующих объектов |
| Тело сохранения пулов | `{...minerConfState, pools: editedPools}` |
| Запись | `POST /cgi-bin/set_miner_conf.cgi`, `Content-Type: application/json`, `JSON.stringify` один раз |
| Ожидаемый ack по форме | HTTP `ok` и `stats == "success"` |
| Отдельный отказ | `stats == "error"`, `code == "M028"`, `msg == "firmware upgrade process"` |

Это полная копия текущего объекта с заменой только пользовательского
массива, без DTO, aliases или defaults. Исходные `index` сохраняются
в объектах `pools`; остальные поля, служебный массив и комиссия
пересылаются без преобразования.

У hotel fee есть отдельная форма сохранения и преобразования процента;
они не относятся к обработчику пользовательских пулов. Скрытая вкладка
hotel fee не разрешает удалять её конфигурацию из полного POST.

## Условия безопасной реализации и границы

В bundle нет обращения к имени `need_update_fw_now`, однако spread
полного конфига автоматически переносит это поле в POST. Его серверные
побочные эффекты не проверены. В текущем чтении отдельный sidecar
подтвердил точное boolean `false`, не экспортируя остальные значения.
Безопасный контракт должен допускать
только точное boolean `false`, проверять это повторно перед записью
и блокировать `true`/неизвестное состояние, а не молча менять флаг.

Нужны точная квалификация по native модели/движку/API, текущим HTML/JS
и полной схеме, копирование сохранённых индексов и всех нетронутых
параметров, повторная идентификация и проверка конфликтов после
предпросмотра. Служебные пулы не подменяются пользовательскими.
Неизвестная схема или скрытое поле не получают значение по умолчанию.

После сохранения пользовательская форма показывает результат ack,
а общий provider опрашивает конфигурацию периодически; обработчик
не ожидает независимого readback. Явного apply/reboot в нём нет.
Это не доказывает отсутствие серверного перезапуска или иных эффектов.
Фактический ответ setter, сохранение и применение на ASIC не проверялись.
Повторный POST при неопределённом результате не допускается.

## Программный адаптер

Добавлен отдельный
[адаптер C096](../../miner_scanner/pitbit_pool_backend.py),
синтетический [fixture](../../tests/fixtures/pitbit_c096_pools_read.json)
и [локальные проверки](../../tests/test_pitbit_pool_backend.py).
Он требует точные native Type/Miner/API, общий профиль `bitmain.pitbit`,
оба хеша HTML/JS, полную типизированную схему из 23 ключей,
индексы `[0, 1, 2]`, один полный служебный слот и точный `false`
флага обновления. Native-ответ должен иметь непустой список `STATUS`
со статусами `S`. Другие PitBit и C074 не получают этот допуск.

Тело строится глубокой копией и изменением только `url/user/pass`
пользовательских объектов. Перед единственным POST заново проверяются
native-идентичность, известные аппаратные идентификаторы, статические файлы
и совпадение всей конфигурации со снимком предпросмотра.
Скрытые поля пользовательских/служебного пула не пересылаются;
обычные ACL wildcard не считаются замаскированными паролями.
Общий механизм выполняет полный readback с проверкой нетронутых данных.
Наличие реализации и локальных сценариев не подтверждает аппаратную запись.
Отдельный локальный сценарий использует настоящий `make_record` из
native VERSION и HTTP system без optional stats и без ручного изменения
FW/API в записи. Та же HTTP-строка с последующим native C074 блокируется;
native C096 проходит полный путь подготовки и исполнения на имитаторе.
Общие drivers и старый C074-контракт не изменялись.

индексы `[0, 1, 2]`, hotel pool/комиссия и `false` флага обновления
сохранены; исходный объект не изменён. Все проверки дали `true`,

Audit содержит 11 записей: **9 HTTP GET и 2 native `version`**,
без POST или других записей. Обезличенный экспорт зафиксировал
`review_status=ready`, backend `pitbit.c096.web.pools`,
source `pitbit.web.conf`. Это проверка подготовки и формирования запроса
в памяти, не подтверждение реальной записи или применения на ASIC.
