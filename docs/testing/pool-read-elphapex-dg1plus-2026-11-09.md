# Elphapex DG1+: чтение конфигурации пулов, 09.11.2026

Проверен один выбранный пользователем Elphapex DG1+, Stock
`DG1+_SW_V1.0.4`, профиль `elphapex.luci`. Разрешено только чтение.
Пулы прочитаны; текущий контракт веб-формы установлен статически.
Приём, сохранение и применение записи на устройстве не проверялись.

IP, MAC/SN, hostname, значения URL/worker/паролей пулов и профили доступа
не включены в отчёт. Полные ответы устройства не сохранялись.
Модель и полная сборка сверены во временном клиенте до обезличивания;
экспорт намеренно скрывает model и часть строки версии. Пустое model
в обезличенном JSON не означает отсутствия модели у устройства.
Версия отдельного API в этом чтении не запрашивалась.

## Успешное чтение

Получены HTTP 200 на:

- `GET /cgi-bin/luci/get_system_info.cgi`;
- `GET /cgi-bin/luci/get_miner_conf.cgi`.

У конфигурации ровно восемь верхних полей; дополнительных полей в этом
ответе не было:

| Поле | Наблюдённый тип |
| --- | --- |
| `pools` | array, три объекта |
| `fc-voltage` | string |
| `fc-fan-ctrl` | boolean |
| `fc-freq-level` | string |
| `fc-fan-pwm` | string |
| `algo` | string |
| `fc-work-mode` | integer |
| `fc-freq` | string |

В каждой из трёх позиций `pools` присутствуют строковые `url`, `user`,
`pass`. Значения паролей не печатались и не экспортировались.
Отсутствующий пароль не заменялся пустой строкой. Получение конфигурации
само по себе не подтверждает тело, приём или применение запроса записи.

Позднее отдельно выполнен `GET /cgi-bin/get_miner_conf.cgi`, который
использует актуальная форма. Набор всех восьми полей и их типы совпали
с LuCI; полное сравнение значений в памяти также вернуло равенство.
В каждой из трёх позиций присутствуют `url/user/pass`. Сохранены только
`same_field_types=true`, `equal_to_luci_in_memory=true`, имена/типы
и состояния присутствия; исходные значения не сохранялись.

## Актуальная веб-форма

Основные страницы `/` и `/index.html` потребовали авторизацию (HTTP 401),
`/miner.html` ответила HTTP 404. В существующем защищённом хранилище
не было подходящего профиля Elphapex для выбранного адреса.
После отдельного разрешения пользователя выполнены только GET с
HTTP Basic для этого же устройства; основная HTML-страница и её
локальные JavaScript стали доступны. Значения доступа в отчёт не включены.

В основном модуле route `/miner` загружает `./Miner-f770af99.js`.
Его зависимости включают `./axios-82afda87.js`. Статическое чтение
компонента `Miner` установило следующий контракт текущей формы:

| Этап | Код текущей формы |
| --- | --- |
| Чтение | `GET /cgi-bin/get_miner_conf.cgi`, затем `t.value = response.data` |
| Редактирование | Для каждого элемента `t.value.pools` прямые привязки к `url`, `user`, `pass` |
| Запись | `POST /cgi-bin/set_miner_conf.cgi`, тело — весь `t.value`, `Content-Type: application/json` |
| Преобразование полей | DTO, aliases и замены дефисов подчёркиваниями отсутствуют |
| Ответ | Любой HTTP 2xx, принятый Axios, вызывает новый GET и сразу показывает Success |
| Применение | Явного reboot, apply или таймера в компоненте нет |

Таким образом, форма сохраняет остальные свойства полученного объекта
в теле запроса, включая неизвестные ей поля. В компоненте есть функция
переключения `fc-fan-ctrl`, однако привязки события к ней в отрисованной
форме нет; кнопка сохранения вызывает только отправку объекта.
Это существенно отличается от создания нового DTO старым инструментом.

Зависимость экспортирует обычный экземпляр Axios 1.5.0 без прикладных
настроек baseURL, auth или interceptors; компонент передаёт лишь JSON
Content-Type. Пути относятся к тому же origin. Библиотечная поддержка
Basic и XSRF не доказывает отдельного требования токена к этому API.
JavaScript и интерфейс браузера не исполнялись.

Форма не проверяет `stats`/`code` ответа и не ждёт результата нового GET
перед сообщением Success. Поэтому этот текст не доказывает успешное
сохранение или применение настроек. Запрос записи при проверке не отправлялся.

## Границы установленного контракта

Из [официального инструмента](../development/elphapex_pool_contract.md)
известен кандидат `POST /cgi-bin/luci/set_miner_conf2.cgi` с JSON и
пулами `url/user/pass`. Его DTO использует имена с подчёркиваниями:
`fc_fan_ctrl`, `fc_fan_pwm`, `fc_freq`, `fc_voltage`, `fc_work_mode`,
`fc_freq_level`; pool-ветка оставляет их `false`/`null`.
Фактическое чтение LuCI DG1+ использует дефисы и дополнительно содержит `algo`.
Автоматическая замена дефисов подчёркиваниями не является доказанным
соответствием полей. Отправлять значения по умолчанию вместо текущих
параметров вентилятора, режима, частоты или напряжения нельзя.

Маршруты текущей формы не содержат `/luci/` и не используют `conf2`.
Совпадение двух getter проверено отдельно, а не выведено из имён.
Квалификация безопасного программного контракта ограничивается DG1+
с этой полной сборкой, всеми восемью полями и текущими HTML/JS.
Записываемый объект должен сохранять типы и значения всех нетронутых
полей/слотов; неизвестная схема или неизвестный пароль блокируют подготовку.
HTTP 2xx сам по себе не подтверждает принятие: точное сравнение свежего
сохранённого конфига может подтвердить конфигурацию, но не ответ API
о принятии и не начало добычи с новыми настройками.
Статический код формы не заменяет проверку записи на оборудовании
в отдельно согласованной операции. На DG1 или другую сборку результат
автоматически не распространяется.

## Реализованный адаптер и подготовка в памяти

В программе добавлен
[адаптер текущей формы](../../miner_scanner/elphapex_pool_backend.py),
синтетический [пример ответа](../../tests/fixtures/elphapex_dg1plus_web_pools_read.json)
и [локальные сценарии проверки](../../tests/test_elphapex_pool_backend.py).
Адаптер допускает только Elphapex/Stock, `elphapex.luci`, модель DG1+,
полную сборку `DG1+_SW_V1.0.4`, все восемь ключей с точными типами,
три полных `url/user/pass` и четыре хеша HTML/JS выше.
Для основного веб-интерфейса используется обычный профиль HTTP Basic;
учётные данные API и пароли пулов — отдельные значения.

Перед однократным POST повторно читаются идентичность, конфигурация
и статические файлы. Изменение состояния после предпросмотра блокирует запись.
Формируется копия всего объекта с изменёнными полями выбранных пулов,
без изменения исходной конфигурации, aliases или defaults.
HTTP 2xx возвращает неизвестное принятие (`None`), а не заимствованный ack.
Общий механизм сверяет полный свежий конфиг: совпадение может подтвердить
настройки чтением при `accepted_by_api=false`, но не применение при добыче.
Повторной записи, apply или reboot нет.

На прочитанной конфигурации выполнены две подготовки в памяти:
worker с суффиксом IP и с порядковым номером. В обеих `ready=true`;
менялись `url/user/pass`, исходящее тело содержало все восемь ключей.
Сохранение нетронутых слотов, nonpool-значений, их типов и неизменность
исходного объекта дали `true`; `setter_called=false`.
Audit этого прогона содержит ровно 15 GET и ни одного POST.
Это проверка программной подготовки запроса, а не аппаратной записи.
