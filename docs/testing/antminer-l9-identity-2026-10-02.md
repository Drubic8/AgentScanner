# Antminer L9: ложная смена идентичности после Sleep

Проверено 02.10.2026 на `10.33.206.11`, стоковая прошивка:
`system_filesystem_version=Mon Feb 10 10:01:06 CST 2025`, API 3.1.
Профиль `bitmain.stock.l9.20250210`.

## Причина

Пользователь успешно отправил Sleep, затем два запроса Normal были остановлены
сообщением «Устройство или прошивка изменились; обновите выбор».

В сохранённой записи версия прошивки была датой сборки, а новое чтение
идентифицировало её как `86.48-2.0.0`. MAC совпадал, модель и профиль также.
Дата находится в `system.system_filesystem_version`; числовой вариант —
в `stats.STATS[1].miner_version`. Рекурсивный поиск выбирал первое доступное
поле, поэтому наличие или порядок телеметрии влияли на отпечаток устройства.

## Изменение

Для парсера Antminer поля прошивки теперь извлекаются из именованных ответов
`version` и `system` с фиксированным приоритетом. Поле `stats.miner_version`
не подменяет системную сборку. Все явные поля прошивки из этих двух ответов
участвуют в отпечатке: изменение любого из них по-прежнему блокирует команду.
Если обязательная идентификационная информация исчезла, она не восстанавливается
из старой телеметрии для обхода проверки. Смена MAC также остаётся сменой устройства.

После обновления исходников требуется перезапустить GUI и обновить сканирование:
записи с прежним способом вычисления отпечатка должны быть заменены свежими.

## Проверка

Через общий `execute_command` отправлен один запрос Normal на указанный L9.
Результат `succeeded`, API принял запись, чтение подтвердило:

| Поле конфигурации | Значение |
| --- | --- |
| `bitmain-work-mode` | `0` (Normal) |
| `bitmain-freq-level` | `100` |
| `bitmain-fan-ctrl` | `false` |
| `bitmain-fan-pwm` | `100` |

Завершение разгона до номинального хешрейта не проверялось.
Дополнительные Sleep/Reboot при этой проверке не отправлялись.

Локальные тесты проверяют исчезновение `miner_version`, недоступность `stats`,
порядок ключей, смену реальной прошивки в обоих источниках, отсутствие сборки
и замену MAC. `python -m unittest discover -s tests -q` — **222 теста прошли**.
EXE не пересобирался.

## Повторный отказ в GUI и проверка полного пути

Пользователь сообщил повторные отказы в 10:07 после нового запуска GUI.
В текущей проверке через `ScanWorker` и два последовательных предварительных
опроса идентификатор и отпечаток совпали; повторный отказ не воспроизведён.
Таким образом, предыдущая правка подтверждена тестами, но точная причина этих
двух повторных отказов по старому общему сообщению не установлена.

Выявлен дополнительный недостаток GUI: `ActionWorker` отдавал только текст
результата. Обновлённая при предварительном опросе идентичность оставалась во
внутреннем сервисе, а выбранная строка продолжала хранить прежние данные.
Теперь worker передаёт актуальную запись в GUI после результата, а после
отправленной команды выполняет один дополнительный опрос состояния.
Повторной отправки команды нет. Таблица обновляет строку по IP, сохраняет
галочку и заменяет данные выбранного устройства без дублирования строки.

Сообщение `skipped` теперь перечисляет изменившиеся поля: модель, версию
прошивки/API, серийный номер, MAC, профиль, метаданные или идентификатор
выбранной строки. Значения личных идентификаторов в сообщение не выводятся.

Аппаратная проверка использовала `GeminiApp.run_action` и `ActionWorker`,
с окнами Qt offscreen и сохранёнными профилями доступа. После сканирования
одного адреса и выбора строки в 10:22:07 Normal завершился `succeeded`:
ответ записи не получен, но конфигурация подтвердила целевой режим.
Идентификатор и выбор строки сохранились; число строк осталось равным одному.
Сразу после пробуждения состояние GUI ещё было `Unknown`; завершение разгона
этим результатом не подтверждается.

Проверены отказ для устаревшей выбранной строки, отсутствие записи в таком
случае, обновление этой строки и последующий успешный Normal на подменах.
Общий набор — **223 теста, все прошли**. Полный GUI smoke-check также прошёл,
включая обновление идентичности строки, сохранение выбора и экспорт отчётов.
