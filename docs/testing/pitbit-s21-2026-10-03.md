# Antminer S21 / PitBit: проверка 03.10.2026

Проверено одно выделенное пользователем устройство `10.33.228.3` через исходники
ASIC Monitor 2.1.0. Другие адреса не получали команд.

## Идентификация

- CGMiner: `Antminer S21_i`, API `3.1`, `miner_version=incm.C074`.
- Веб-интерфейс: `Antminer S21(PitBit.78)`, контроллер `AMLCtrl_BHB68XXX`.
- HTTP system build: `Fri Feb 2 17:03:40 CST 2024`.
- Профиль: `bitmain.pitbit.s21.c074.20240202`.

Обозначения PitBit.78 и incm.C074 относятся к разным ответам устройства.
Номер движка не следует выдавать за номер пакета веб-прошивки. Проверенный профиль
ограничен моделью, сборкой HTTP, версией движка и API. Неизвестная сборка остаётся
в общем профиле PitBit; изученные стандартные режимы Stock она не наследует.

## Результаты

| Действие | Запрос | Ответ / подтверждение |
|---|---|---|
| LED ON | `POST /cgi-bin/blink.cgi`, `{"blink":true}` | `B000`; отдельное чтение `blink=true`; программа `succeeded` |
| LED OFF | тот же путь, `{"blink":false}` | `B100`; отдельное чтение `blink=false`; программа `succeeded` |
| Sleep | `POST /cgi-bin/set_miner_conf.cgi`, `{"bitmain-work-mode":"1"}` | `stats=success`, `code=M000`; режим 1; текущий хешрейт снизился до 0, состояние `stopped` |
| Wakeup | тот же путь, `{"bitmain-work-mode":"0"}` | `M000`; режим 0; проверка возвращения добычи описана ниже |
| Reboot | один `GET /cgi-bin/reboot.cgi` | ответ оборвался по ReadTimeout; устройство вернулось, uptime 142 → 30 с, прежняя идентичность; затем появился хешрейт 61.35 TH/s |
| Low / High / HEM | не отправлялись | стандартные команды не подтверждены; наличие настроек частоты не разрешает угадывать режим |

LED подтверждён по API. Визуальный осмотр индикатора пользователем ещё не выполнен.
Результат Reboot в журнале команды остаётся `unconfirmed`: сетевой таймаут сам по
себе не подтверждает перезагрузку. Аппаратный результат установлен последующим
наблюдением uptime и возврата майнинга; повторная команда не отправлялась.

## Исправления

1. Обработчик PitBit принимает `M000` именно для записи режима. Явный отказ API
   по-прежнему возвращает `failed`; успешный ответ без совпавшего чтения режима —
   `unconfirmed`. Перед записью выполняется повторная идентификация устройства.
2. Проверенные Sleep/Wakeup доступны без экспериментального переключателя.
   В запрос передаётся только поле режима: пулы, напряжение, частота и охлаждение
   не пересылаются и не подменяются.
3. При режиме Sleep и остаточном текущем хешрейте отображается `Stopping`.
   Измеренное значение `GHS 5s=0` не заменяется положительным `rate_30m`.
   Нулевой текущий хешрейт вместе с режимом 1 даёт `Sleep` / `stopped`.

Первый прогон обнаружил ложный отказ `M000`; после исправления четыре команды
LED ON/OFF, Sleep/Wakeup повторно прошли обычным путём управления, без
`allow_unverified`. Дополнительный цикл подтвердил фактическую остановку добычи.
В нём процесс наблюдения ещё использовал загруженный до исправления парсер;
отдельный процесс с новым кодом подтвердил режим 1, хешрейт 0 и `stopped`.

## Восстановление и границы проверки

После первого цикла и перезагрузки полная конфигурация совпала с исходной.
Сравнение SHA256 включало пулы и все параметры питания, частот и охлаждения;
значения учётных данных в отчёт не записывались. Исходное состояние: режим 0,
LED выключен.

Финальное пробуждение подтверждено: режим 0, состояние `running`, сначала
0.549 TH/s, затем отдельный опрос показал 55.193 TH/s и работу трёх плат.
Полная конфигурация снова совпала с исходной, LED выключен.
Разгон до номинальной производительности, режимы изменения мощности и длительные
стресс-тесты в этот прогон не входят.

успешный цикл, сохранность конфигурации, явный отказ, отсутствие readback,

однократная перезагрузка и переход в сон с положительным историческим средним.

новых проверок PitBit и существующие проверки GUI. Qt запускался с
`QT_QPA_PLATFORM=offscreen`; сеть и оборудование в этих тестах подменены.

пароли, токены, адреса пулов и воркеры не экспортировались.
